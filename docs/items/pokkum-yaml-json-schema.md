## Summary

`schema/pokkum.schema.json` is generated by reflection over the real config structs, so editors get inline validation and completion without a hand-written schema that could drift.

## Decision

Generated by `scripts/gen-schema` from `ports.ProjectConfig`/`ports.BuildProfile` rather
than authored, because a hand-written schema is a second description of the same types and
would drift from the parser. `make schema` regenerates; `make check-schema-freshness`
asserts regeneration is a no-op and is wired into `make verify` beside the docs guard.

Enum values are read from the constants the code actually validates against — `strategy`
from `ports/compiler.go`, `runtime` from `ports/runtime.go`, `fail_on_cve` from
`ports/scanner.go`, `sbom` from `ports/sbom.go`, `cache.verify_mode` from
`RemoteCacheVerifyMode.Valid`, `deploy` from `ports/deploy.go`, and the profile-only
`output` from core's `OutputMode`.

Two judgement calls: `base` is deliberately not an enum, since
`core.ParseBaseImageSpec` accepts the three presets *or* an arbitrary image reference and
an enum would reject every valid custom base; and `additionalProperties: false` is emitted
only because the loader really does call `KnownFields(true)`, with map-typed fields
(`labels`/`annotations`/`env`, `profiles`) getting a value schema instead since their keys
are open-ended by design.

Validated without adding a dependency: the tests implement only the keywords the generator
emits, against the values `yaml.v3` already decodes.

## Known Limitations

- Cross-field rules are not encoded: the deploy target/method matrix and the runtime/strategy/base composition. Both need JSON Schema conditionals for constraints `pokkum config validate` already enforces; the field descriptions say the schema does not check them rather than implying it does.
- The schema is not reachable from the CLI — see item config-schema-subcommand.
