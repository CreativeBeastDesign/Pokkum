# Pokkum Architecture & Technical Deep-Dive

**Pokkum** is a Go-based zero-dependency OCI image builder and deployment pipeline tool specifically designed for SvelteKit applications (using `--strategy=layered` N-layer layout by default, or `--strategy=exe`).

It builds multi-architecture OCI images (`linux/amd64`, `linux/arm64`), embeds a PID-1 supervisor, generates Software Bills of Materials (SBOMs), and pushes reproducible container images directly to OCI registries — **without requiring Docker or a Docker daemon**.

See also [docs/archive/fixes-to-v1.md](docs/archive/fixes-to-v1.md) for a post-v1.0 audit and the
fixes it produced.

---

## 1. High-Level System Architecture

Pokkum is structured using **Hexagonal Architecture (Ports and Adapters)** to decouple core domain logic from external tools, operating systems, and network registries.

**Automated purity verification (`internal/architecture_test.go`, run via `go test ./internal/...` or `make check-arch`)** enforces this via AST analysis, not just code review convention. Beyond the core/ports-never-imports-adapters rule described throughout this document, it also checks: adapters must not import each other directly — **the allowlist for this rule is empty as of 2026-08-19** (it held seven real edges as of 2026-08-18; see "Composition Root & Verifier Wiring" below for how the last of them closed); `internal/core`/`internal/ports` must not import any `*utils` package (utility packages sit alongside adapters, not beneath core, even though they carry no adapter-interface implementation); and every `switch` over a string-enum family (`ports.BuildStrategy` and similar) must have a `default` arm, so an unhandled future enum value fails loudly instead of silently falling through. The inverse direction — "a `*utils` package must not import `core`" — is deliberately NOT enforced: it is false on legitimate code, since outer layers may depend inward.

### Composition Root & Verifier Wiring (fixed 2026-08-19)

`baseimage`, `provenance`, and `remotecacheutils` used to each construct their own `cosign.NewSigner`/`sigstore.NewVerifier` default when the caller didn't supply one — a real adapter reaching into another adapter's package, exactly the edge the architecture test's allowlist existed to flag as a documented gap rather than a sanctioned pattern. Those defaults are now deleted, not relocated: **`cmd/pokkum` is the only place any of the three verifiers gets constructed**, injected as an option at every call site. A verifier stays optional at the type level (e.g. `pokkum base check` lists digests and never verifies, and shouldn't have to build a real Sigstore verifier just to do that), but a construction site that verifies without one now fails closed with a new `provenance.ErrVerifierNotInjected` rather than silently skipping the check — enforced structurally, not by convention: a dedicated composition-root test AST-scans every non-test file in `cmd/pokkum` and fails if any of the three constructors is called without its verifier options (and fails if it finds *zero* call sites at all, so it can't go vacuous under a future rename). The remaining three of the original seven allowlisted edges were adapters reaching into `sigstore` purely for its Cosign annotation-name constants and `ErrNoBundle`; that shared wire vocabulary now lives in `internal/ports` instead (`sigstore.ErrNoBundle` aliases the new `ports.ErrNoKeylessBundle`), so a consumer of the port can reach it without importing the implementation. Deleting the defaults exposed two previously-unreachable fail-opens in `provenance` — a nil-signer branch with no `default` arm, and a nil-keyless check folded into a material-presence test — both closed via `provenance.ErrVerifierNotInjected`; see `Lessons.md`'s 2026-08-19 entry.

The same rule now covers *material*, not only constructors. `ports.BaseImageRequest.TrustedRootJSON` used to be `TrustedRootPath string`, read with `os.ReadFile` inside the `baseimage` adapter — the odd one out among Pokkum's three Sigstore trust-root consumers, the other two (`sigstore.Verifier`'s `trustedRootJSON` and the TUF refresh option) already taking bytes. It takes bytes as of 2026-08-19: `cmd/pokkum` reads any `--sigstore-trusted-root` file **once**, hands the same bytes to both the base-image and the remote-cache verification paths, and no adapter touches the filesystem for it. Two consequences worth knowing. A trust root obtained from a live TUF refresh can now be handed to any of the three without a temp file, which is what made this a deliberate non-decision when the refresh flag was wired. And an unreadable `--sigstore-trusted-root` now fails the command closed (wrapping `core.ErrBaseSignatureInvalid`) *before* the build starts rather than mid-resolve — it previously only failed if keyless verification actually ran, and the cache-verification consumer swallowed the read error entirely and degraded to the embedded snapshot while the operator believed their explicit root was in force. Verifying against a root nobody asked for is the exact substitution the flag exists to prevent.

### Core Layers

1. **CLI Layer (`cmd/pokkum/`)**:
   - `build.go`: Parses flags (`--platform`, `--tag`/`-t`, `--base`, `--runtime` (`bun`|`node`, default `bun` — see §8's Runtime Dimension), `--sbom`, `--sbom-attach`, `--local`, `--tarball`, `--update-base`, `--offline`, `--bun-binary`, `--bun-variant`, `--image-label`, `--base-verify-mode`, `--base-keyless-identity`, `--base-keyless-issuer`, `--sigstore-trusted-root`, `--no-verify-base`, `--allow-secret-pattern`, `--require-env`, `--fail-on-cve`, `--allow-incomplete`, `--vex-output`, `--hermetic`, `--registry-config`, `--sign`/`--no-sign`, `--signing-key`, `--require-signed`) and invokes the core build pipeline. Resolves `SOURCE_DATE_EPOCH` first, then unconditionally calls `git_metadata.go`'s `discoverGitMetadata` to auto-populate `org.opencontainers.image.revision`/`.source`/`.version` (from `git`/CI env vars) and `.created` (set to the already-resolved build timestamp, never independently re-derived) before any explicit `--image-label` values are merged in (explicit values win).
   - `scan.go`: Implements `pokkum scan [target]` for security vulnerability scanning, OSV advisory lookups (`--toolchain`), threshold enforcement (`--fail-on`), offline scanning (`--offline`), incomplete scan handling (`--allow-incomplete`), and JSON reporting (`--output=json`).
   - `dev.go`: Implements `pokkum dev [dir]` subcommand for local container development, supporting `--debug` interactive shell debugging, local Docker daemon loading, and hot-reload source watching. **`--no-container` (added 2026-08-19, Roadmap Tier 1.2 item 6a)** is a parallel, deliberately separate local seam: it skips image construction entirely and runs the project's own dev server (`bun run dev`) directly on the host, rather than reimplementing a second watch/rebuild loop on top of Vite/SvelteKit's own HMR. Its guarantees are explicitly and only a subset of the default container-parity mode's — a startup warning states it has none of a real Pokkum image's supervisor, startup attestation, probes, base image, or non-root user, and does not reproduce production. Flags that describe an image that's never built (`--debug`, `--platform`, `--bun-version`, `--bun-variant`) are rejected outright; `--port`/`--watch` only warn when explicitly set (the dev server picks its own port; hot reload is inherent to it, not opt-in); `--bun-binary`/`--env-file` remain meaningful and are handled locally rather than handed to a daemon.
   - `doctor.go`: Implements `pokkum doctor [dir]` for environment preflight checks (Bun runtime, registry credentials, SvelteKit version compatibility, `.pokkumignore` sanity, base image security) and mechanical repairs (`--fix`).
   - `init.go`: Implements `pokkum init [dir]` subcommand to bootstrap project configuration and `.pokkumignore`.
   - `explain.go`: Implements `pokkum explain <image>` and its `pokkum explain why <image> <file-path>` / `pokkum explain diff <image1> <image2>` subcommands (not top-level commands). All three read a real OCI image (registry ref or local `.tar`) and report real per-layer digests/sizes/file counts/purposes (the last derived from the image's own `ConfigFile().History`, no static layer-count table), real file-origin tracing (including whiteout/opaque-whiteout deletion detection), and real per-layer/per-file diffs between two images (`--platform`, `--registry-config`).
   - `verify.go`: Implements `pokkum verify <ref>` subcommand for rebuild verification and SLSA provenance attestation validation (`--no-rebuild`, `--expect-source`, `--against`, `--registry-config`, `--keyless-identity`, `--keyless-issuer`, `--public-key`, `--sigstore-trusted-root`). The expected keyless identity comes exclusively from `--keyless-identity`/`--keyless-issuer` (fixed 2026-08-18) — never derived from the certificate under verification; see §6 below.
   - `repro_doctor.go`: Implements `pokkum repro doctor [dir]` for stage-level non-determinism bisection (`--fast`, `--perturb`).
   - `base.go`: Implements `pokkum base update` and `pokkum base check` subcommands to query remote base image digests, manage `pokkum.lock`, and escrow mirror base images and Cosign `.sig` tags (`--mirror-registry`).
   - `adopt.go`: Implements `pokkum adopt [dir]` migration codemod to convert existing SvelteKit apps (`adapter-node`, `adapter-vercel`, `adapter-auto`, `adapter-cloudflare`) to Pokkum compilation defaults, rewriting `package.json`/`svelte.config.js`, bootstrapping `.pokkumignore`, and optionally deleting legacy Dockerfiles (`--dry-run`, `--remove-dockerfile`).
   - `history.go`: Implements `pokkum history <image>` subcommand for inspecting image provenance timelines, SLSA attestations, Cosign signatures, builder metadata, and CI workflow run links (`--expect-source`, `--output=json`).
   - `resolve.go`: Scans Kubernetes YAML manifests for `pokkum://` image URIs, triggers automated builds, and resolves them to immutable image digests (`repo@sha256:...`), supporting `--registry-config`.
   - `apply.go`: Resolves `pokkum://` manifests and pipes the output directly into `kubectl apply -f -`, supporting pre-flight live cluster annotation inspection (`--cluster-inspect`, `--no-cluster-inspect`) and `--registry-config`.
   - `rollback.go`: Implements `pokkum rollback -f <manifest> [--to=<ref>]` for rolling back container image references in Kubernetes manifests across multiple generations using `pokkum.dev/image-history` annotations (`-g`, `--generation=<n>`, `--list`) or an explicit target reference (`--to`).
   - `upgrade.go`: Implements `pokkum upgrade` for release checking (`--check`), signature verification via `ports.ReleaseVerifier`, and self-updating.
   - `k8s.go`: Shared manifest parsing, security context/network policy injection, and URI replacement engine.
   - `version.go`: Displays git version, commit, and build timestamp metadata.

5. **Public Packages (`pkg/`)**:
   - `registry`: Ephemeral in-memory OCI 1.1 test registry server utility (`pkg/registry.NewServer()`) for integration testing and local development.

2. **Domain Core (`internal/core/`)**:
   - `pipeline.go`: Orchestrates the execution flow across compilers, base image resolvers, packagers, and registries, supporting `PinnedBuildInputs` override parameters.
   - `model.go`: Defines domain models (`BuildRequest`, `Platform`, `RuntimeConfig`, `ImageRef`, `BunRuntimeOptions`, etc.).
   - `errors.go`: Defines standardized domain error types (`ErrPackageFailed`, `ErrUnsupportedPlatform`, `ErrBunResolutionFailed`, etc.).

3. **Abstraction Ports (`internal/ports/`)**:
   - Interfaces decoupling core logic from external adapters: `Compiler`, `Packager`, `Registry`, `BaseImageResolver`, `BunRuntimeResolver`, `SBOMGenerator`, `SupervisorProvider`, `K8sResolver`, `Signer`, `Attestor`, `BinaryInspector`, `ProvenanceResolver`, `ImageComparator`, `ReleaseVerifier`, `SecretGuard`, and structured output envelopes (`JSONEnvelope`, `OutputFormat`).

4. **Adapter Implementations (`internal/adapters/`)**:
   - Every concrete adapter package enforces explicit compile-time interface assertions (e.g., `var _ ports.BaseImageResolver = (*Resolver)(nil)`) to guarantee immediate compile-time detection of port contract drift.
    - `bunexec`: Manages SvelteKit preparation and compilation. Supports Option B zero-config virtual Vite config injection (`.pokkum/vite.config.ts`), invoking `bunx vite build --config .pokkum/vite.config.ts` without mutating user-authored files, with fallback to Option C `checkEffectiveAdapter` fail-fast validation.
    - `bunruntime`: Resolves, downloads, SHA256-verifies, and caches official Bun runtime binaries (`~/.cache/pokkum/bun`) or compiles and caches hardened minimal stub entrypoint launchers (`stubs/<version>/<variant>/<platform>/bun`) when `StubLauncher` (`--stub-launcher`) is enabled. Supports local custom binary bypass (`--bun-binary`). Integrity verification: statically pinned SHA256 digests for a small set of common versions (fast, network-free), and for any other `--bun-version`, GPG signature verification of Bun's own `SHASUMS256.txt.asc` release manifest against an embedded release-signing public key — fails closed on any fetch/signature/checksum failure.
    - `packager`: Constructs reproducible OCI tarballs, custom single-binary layers (`BuildCustomFileLayer`), directory tree layers (`BuildDirectoryTreeLayer`), and multi-arch index manifests using `github.com/google/go-containerregistry`.
   - `baseimage`: Resolves base image layers (`gcr.io/distroless/cc-debian12:nonroot` or Chainguard `glibc-dynamic`), verifies base image signatures (static-key via `ports.CosignSigner` for custom/self-signed bases, or keyless Sigstore via `ports.KeylessVerifier` for stock presets), and maintains `pokkum.lock` digest locks. Supports base image escrow mirroring via `--mirror-registry` on `pokkum base update`, copying base images/indexes and their associated Cosign `.sig` tags with automated `MirrorRef` fallback in `pokkum.lock`. **`--base` accepts a full custom image reference, not only the four fixed presets (fixed 2026-08-19)** — `cmd/pokkum/build.go` tries the fixed preset names first, and only parses a value containing `/`, `.`, `:` or `@` as a reference, so a misspelled preset is rejected with the list of valid ones rather than becoming a Docker Hub shorthand lookup (`name.ParseReference` would otherwise happily accept a typo like `distrolss` and fail much later at pull time). A custom reference defaults to static-key verification, which fails closed since the placeholder trust anchor no longer exists. **Lock keying (per-reference slots for custom bases, closed 2026-08-19):** `Resolve` keys `pokkum.lock` entries via `lockKeyFor(preset, ref)`. The fixed presets keep their historical bare-preset-name key — each preset string already names one specific upstream image, which is the reason `distroless-node` is its own preset rather than a `Ref` override — and must keep it, since re-keying them would orphan every pin in every existing lockfile. `BaseImageCustom` cannot follow that pattern (one preset value covers every reference a project might name), so custom entries get `"custom:" + sha256(normalized ref)[:12]`: two custom bases in one project each hold their own stable pin instead of the second evicting the first. Three properties are load-bearing. (1) The pre-existing `Ref`-match guard is deliberately **kept** on top of the new keying, not replaced by it: a truncated hash can collide and `pokkum.lock` is hand-editable, so a locked entry is only trusted when its recorded `Ref` names the reference being resolved (and, for scan-metadata/mirror carry-over, its `Digest` matches the digest just pulled). Without it, resolving custom base B after A had locked used to trust A's entry and silently return A's image content for a B request. (2) **Migration**: a lockfile written before per-reference slots holds its custom pin under the bare `"custom"` key; that slot is still *read* as a fallback, subject to the same `Ref` match, and when honoured the entry is copied verbatim under the per-reference key and the legacy one dropped — so an existing pin migrates rather than being silently discarded and re-pulled. The legacy key is never written. A bare `"custom"` entry belonging to a *different* reference is neither trusted nor deleted (it is still that reference's only pin). (3) Anything walking an arbitrary lockfile back to a preset (`pokkum base check`, `pokkum doctor`) must go through `lockfileutils.PresetNameForLockKey`, which maps `custom:<hash>` back to `custom`; parsing a slot name as a preset directly drops every custom base from the output. See `Lessons.md`'s 2026-08-19 entries.
   - `sigstore`: Implements `ports.KeylessVerifier` to verify Sigstore keyless signatures (Fulcio certificate chain + Rekor transparency log inclusion) using `github.com/sigstore/sigstore-go`, against an embedded public-good trust root snapshot. `Verify` itself is always fully offline (no live TUF fetch on the verification path), enabling verification in `--offline`/`--hermetic` builds. Trust-root refresh model (fixed 2026-08-19, closing a real gap where the embedded snapshot was already rejecting valid signatures — see §6): the snapshot is regenerated from the raw, TUF-signature-verified `trusted_root.json` fetched from Sigstore's live TUF repository, with an opt-in TUF client (`tufrefresh.go`, `TUFOptions`) available for callers that explicitly want a live refresh — its `Offline` field fails closed with `core.ErrHermeticViolation` before constructing a network client at all, so hermetic callers can safely hold a reference to it without risking egress. Three guards keep the snapshot from rotting silently: an always-on age/expiry test (`TrustedRootMaxAge`, `TrustedRootExpiryWindow`), a network divergence test against the live repository that skips (never fails) when unreachable, and a digest tripwire against a provenance sidecar (`trusted-root-metadata.json`) recording the snapshot's capture date and SHA-256. The refresh procedure is the same divergence test run with `POKKUM_UPDATE_SIGSTORE_TRUSTED_ROOT=1` (Go's golden-file `-update` convention), so detection and repair share one code path and cannot drift apart. Not yet wired to a CLI flag — `--sigstore-tuf-refresh` is tracked in `docs/Roadmap.md`.
   - `scanner`: Implements `ports.Scanner` for security vulnerability scanning (`pokkum scan`). Catalogs container images, tarballs, and project workspaces using lightweight zero-dependency native parsers (`scannerutils`), queries OSV.dev in high-performance batches (`/v1/querybatch`) for ecosystem-aware OS package CVE lookup (Debian, Ubuntu, Alpine, Wolfi, Chainguard, npm), and enforces severity thresholds (`--fail-on`).
   - `scannerutils`: Utility package providing zero-dependency native parsers for Debian `dpkg/status`, Alpine `apk/db/installed`, `os-release`, and Node.js lockfiles (`bun.lock`, `package-lock.json`, `pnpm-lock.yaml`).
   - `pruneutils`: Utility package providing junk-file blocklisting and directory pruning for `/app/vendor` layer optimization (`*.d.ts`, `*.map`, `tsconfig.json`, `README*`, tests). `PruneOptions.ExcludeDirs` additionally skips named top-level subdirectories entirely (via `filepath.SkipDir`), even under `NoPrune: true` — used by the `/app/server` layer to exclude `client`/`vendor`/`native`/`prerendered`, which are packaged into their own layers separately.
   - `precompressutils`: Utility package providing build-time static asset pre-compression for `/app/client` web assets, format selection per `PrecompressOptions{Gzip, Brotli, Zstd bool}`. The layered strategy requests `.gz`/`.br` only (adapter-node's bundled `sirv` server never negotiates zstd); `--strategy=static` requests all three, including `.zst`, which `pokkum-static` serves. Both its own gzip writer and `packager/layer.go`'s OCI layer gzip codepath are pinned to `github.com/klauspost/compress/gzip` rather than stdlib `compress/gzip`, so compressed bytes are stable across Go toolchain versions.
   - `striputils`: Utility package providing build-time stripping of unneeded debug symbols from native `.node` ELF addons and `.so` shared libraries in `/app/native` and `/app/vendor`.
    - `attestutils`: Utility package defining the shared startup-attestation record/digest algorithm (`Record`, `RootDigest` — sha256 over `<rel>\x00<sha>\n` records globally sorted by rel). Used by the packager (computes the expected digest while building layers) and mirrored verbatim by `pokkum-init` (re-derives it from the live `/app` tree); parity is pinned by `attestutils_test.go`'s mirrored-walk tests.
   - `remotecacheutils`: Utility package implementing `ports.RemoteCacher` for composite build input hashing (`sha256(source + lockfile + baseDigest + bunVersion + platforms + flags)`), sub-100ms remote registry cache querying, pre-promotion cryptographic Cosign/Sigstore signature verification, and tag reconciliation.
   - `poolutils`: Utility package managing `sync.Pool` allocation recycling for 64KB I/O copy buffers and bounded `bytes.Buffer` instances to eliminate GC thrashing during tar archiving, layer streaming, hashing, and pre-compression.
   - `layercacheutils`: Utility package managing local on-disk caching (`~/.cache/pokkum/layers/`) for immutable layer blobs (Bun runtime, `pokkum-init` supervisor) to skip tarring and compression.
   - `lockfileutils`: Utility package for loading, parsing, and saving `pokkum.lock` base image lockfiles, tracking `pinned_ref`, `mirror_ref`, `last_scanned_at`, `vulnerabilities_count`, and `max_severity`. Also owns the lock-slot naming vocabulary shared with `baseimage` and the CLI: `CustomLockKeyPrefix` (`"custom:"`, the namespace for per-reference custom slots) and `PresetNameForLockKey` (maps any slot name back to its preset name). `GetLockedBase` falls back to case-insensitive and `Ref`-based matching; `DeleteLockedBase` deliberately does **not** — a lookup that guesses wrong costs nothing, a delete that guesses wrong discards a pin the caller never named.
   - `jsonutils`: Utility package for structured, versioned JSON response formatting (`--output=json`).
   - `diagnosticsutils`: Utility package for container exit failure analysis and log tracing.
   - `layerdiffutils`: Utility package for entry-by-entry tar merge-walking and header/content diff heuristics.
   - `provenance`: Adapter resolving remote SLSA provenance statements and Cosign attestations.
   - `comparator`: Adapter performing L1/L2/L3 multi-level image digest and file diff comparisons.
   - `registry`: Handles OCI registry authentication (including per-registry auth chains from a `docker config.json`-style file via `--registry-config`), blob uploads, and index pushes.
   - `registryutils`: Utility package for resolving Docker `config.json` auth keychains, executing dynamic credential helpers (`credHelpers`, `credsStore`), and caching credentials in-memory.
   - `sbom`: Generates deterministic SPDX 2.3 or CycloneDX 1.5 SBOMs natively without external cataloger dependencies. Catalogs npm packages from the project's lockfile plus, when `SBOMRequest.BunVersion` is set, the embedded Bun runtime as its own component (`pkg:generic/bun@<version>`, with a `hashes`/`checksums` block when `BunSHA256` is set) — the same purl convention `slsa`'s dependency descriptor uses.
   - `supervisor`: Embedded `pokkum-init` supervisor binary assets (`/pokkum/init`), stored zstd-compressed to shrink the CLI footprint and decompressed on-the-fly to the raw ELF by `ports.SupervisorProvider`.
    - `k8s`: Kubernetes manifest inspection, document rewriting, and `pokkum://` schema resolution.
    - `gitutils`: Utility package for git-based monorepo affected-project detection (`ports.AffectedDetector`, `--since` on `resolve`/`apply`), declaring `const IsUtilityPackage = true`. It diffs each project tree against a base ref (`git diff --name-only <ref> -- .`) plus a `git status --porcelain` check for untracked/staged/deleted changes, validating the ref via `rev-parse --verify <ref>^{commit}` and failing closed on git errors.
   - `sveltekit`: Checks `@jesterkit/exe-sveltekit` adapter installation in target projects.
   - `cosign`: Signs OCI images, attaches Cosign signatures to OCI registries, and implements `ports.ReleaseVerifier` for release signature and SHA-256 checksum verification.
   - `secretguard`: Build-time pattern scanner (`ports.SecretGuard`) — five fixed regex patterns (private key headers, AWS access keys, GitHub PATs, Google API keys, generic password/secret/token assignments); no Shannon-entropy analysis despite the similarly-named class of tool, tracked as future work. Runs in two phases (since 2026-08-18, see §6): pre-build against project source, and post-build against the actual packaged output — scoped per strategy (whole output tree for `layered`; `client/`+`prerendered/` for `static`; asset-overlay content included; for `exe`, its full pre-compile bundled-JS input — both `prep.OutputDir` and the compile entrypoint's own directory, which is not always inside it, e.g. the `--telemetry` wrapper written to `.pokkum/`— since a compiled binary can't be text-scanned with acceptable false-positive/negative behaviour; the residual gap for `exe` is a secret injected by the `bun build --compile` step itself rather than present in the bundled JS, a documented gap not implied covered). A file too large or unreadable to scan is recorded as a skip and fails the build (`core.ErrSecretScanIncomplete`), distinct from a genuine `ErrSecretInlined` finding — "could not look" is never reported as "found nothing."
   - `envbake`: Implements `ports.EnvBakeDetector`, wrapping `sveltekitutils.DetectStaticEnvBindings`'s source scan behind the port boundary so `internal/core` can trigger `$env/static/*` detection without importing an adapter/utility package directly. Optional, like `SecretGuard` — nil means no detection/warning/annotation.
   - `slsa`: Generates SLSA v1.0 provenance predicate statements.
   - `dsse`: Wraps attestations in Dead Simple Signing Envelopes (DSSE).
   - `config`: Implements `ports.ConfigManager` for reading, writing, and validating `.pokkum.yaml` project configurations, evaluating build profiles (e.g. `local`, `production`), and enforcing precedence: explicit CLI flags > environment variables > profile overrides > top-level config defaults.
   - `ignore`: Reads `.pokkumignore` patterns to exclude unwanted files (`.env.local`, source maps, fixtures).
   - `nativeinspect`: Inspects compiled binaries (`DT_NEEDED`, glibc symbols) to ensure base image compatibility.



5. **PID-1 Supervisor Subproject (`supervisor/cmd/pokkum-init`)**:
   - A standalone Go program cross-compiled to `linux/amd64` and `linux/arm64` and embedded in Pokkum.
   - Acts as `ENTRYPOINT ["/pokkum/init", "--", "/app/server"]`.
   - Handles PID-1 duties (reaping zombie sub-processes, forwarding OS signals like SIGTERM/SIGINT).
   - Serves HTTP health endpoints (`/healthz`, `/readyz`) on `POKKUM_PROBE_PORT` (default: 8081).
   - **Fast startup overlap**: `main` resolves the child executable up front (`resolveChildPath` → `New(..., WithChildPath(...))`), so `start()` forks immediately with no `exec.LookPath` on the fork path; the probe listener binds `/healthz` on its own goroutine concurrently with the Bun fork/exec rather than serializing after it. Guarded by `startup_test.go`.

## 2. End-to-End Execution Flow (`pokkum build`)

```
   1. Discover & Validate SvelteKit App
      (check @jesterkit/exe-sveltekit & .pokkumignore)
                  │
                  ▼
     2. Build SvelteKit App JS Entry
      (bun run build via exe adapter)
                  │
                  ▼
    3. Fix Non-Deterministic Artifacts
       (Sort assets.generated.ts)
                  │
                  ▼
   4. Cross-Compile Standalone Binaries
      (bun build --compile per platform)
                  │
                  ▼
   5. Inspect Binary Dependencies
      (nativeinspect DT_NEEDED check)
                  │
                  ▼
      6. Construct OCI Image Layers
     (Base + /pokkum/init + /app/server)
                  │
                  ▼
     7. Assemble Multi-Arch OCI Index
                  │
                  ▼
   8. Supply Chain: SBOM, SLSA, DSSE & Cosign
                  │
                  ▼
     9. Push to Registry / Export Image
```

### Detailed Pipeline Steps

1. **Project Validation**:
   - Checks that target directory contains `package.json` and `@jesterkit/exe-sveltekit` in dependencies.
   - Parses `.pokkumignore` to establish exclusion patterns.
2. **SvelteKit Adapter Run**:
   - Invokes `bun run build` inside the app directory. The `@jesterkit/exe-sveltekit` adapter builds the SvelteKit application and generates a standalone TypeScript server entrypoint along with embedded static assets.
3. **Determinism Stabilization**:
   - Reads `SOURCE_DATE_EPOCH` (or git commit timestamp) to pin all file timestamps (`mtime`).
   - Fixes known non-deterministic outputs (e.g. sorting asset manifests).
4. **Cross-Compilation (`bunexec`)**:
   - For each target platform (`linux/amd64`, `linux/arm64`), runs `bun build --compile --target=<platform>`.
   - Produces a single binary (~90 MB) embedding all JS code, Node/Bun polyfills, and static assets.
5. **Binary & Base Image Compatibility Inspection (`nativeinspect`)**:
   - Reads ELF `DT_NEEDED` dynamic links on built binaries to verify compatibility with glibc in the target base image.
6. **OCI Layer Assembly (`packager`)**:
   - Resolves the requested base image (`gcr.io/distroless/cc-debian12:nonroot` or Chainguard).
   - Employs **Single-Pass Layer Hashing & Streaming** (`buildSinglePassLayer`): Simultaneously calculates uncompressed `DiffID` and compressed `Digest` while streaming tar archives into compressed temporary layers, eliminating multiple disk passes and answering `v1.Layer` queries in `O(1)` time.
   - Appends **Supervisor Layer**: Adds `/pokkum/init` executable with pinned USTAR tar headers (`uid=65532`, `gid=65532`, `mode=0555`), leveraging `layercacheutils` on-disk caching.
   - Appends **Application Layers**: Adds `/app/server`, `/app/client`, `/app/node_modules`, `/app/vendor` (both with `pruneutils` junk stripping), `/app/native`, and `/usr/local/bin/bun`.
   - `/app/node_modules` carries the project's **production dependencies**, installed from its lockfile by `bunexec`'s vendor step into a staging tree under `.pokkum/`. The mount point is load-bearing: Node and Bun resolve a bare import by walking *up* from the importing file, so `/app/server/index.js` consults `/app/server/node_modules`, then `/app/node_modules` — and never `/app/vendor`. Without this layer the image is not self-contained, because Vite externalises dependencies during the SSR build and the server bundle keeps bare imports; Bun's runtime auto-install then fetched them from npm inside the running container, executing code that was in neither the SBOM, the signature, nor the provenance.
7. **OCI Manifest & Index Generation**:
   - Generates OCI Schema 1 Manifest for each architecture.
   - Combines single-arch manifests into a multi-arch OCI Image Index.
8. **Supply Chain Attestation & Signing**:
   - Generates deterministic SPDX/CycloneDX SBOM natively via `sbom` adapter.
   - Generates SLSA v1.0 provenance attestations wrapped in DSSE envelopes.
   - Signs images using Cosign if configured.
9. **Publishing / Exporting**:
   - Pushes layers, index, signatures, and attestations to `POKKUM_DOCKER_REPO` via `google/go-containerregistry`.
   - If `--local` is specified, loads the image into local Docker daemon.
   - If `--tarball` is specified, writes an OCI tar archive.

## 3. How Determinism & Reproducibility Are Achieved

Pokkum guarantees that **identical source code produces identical image digests (`sha256:...`)**.

To achieve this without a Docker daemon:

| Source of Non-Determinism | How Pokkum Pins / Neutralizes It |
|---|---|
| **Host System Clocks** | All tar entry timestamps (`mtime`), OCI image creation timestamps, and history records use `SOURCE_DATE_EPOCH` (derived from git commit timestamp). Nanoseconds are truncated. |
| **Tar Header Metadata** | Uid/Gid are forced to `65532:65532` (`nonroot`), Uname/Gname are wiped, permissions are fixed to `0555`, and format is pinned to `PAX/USTAR`. |
| **Directory Iteration Order** | Go map keys and file listings are explicitly sorted before generating archive entries or config annotations. |
| **Gzip Compression Header** | `tarball.LayerFromOpener` uses gzip with zeroed headers (no filename, zero mtime) so compressed layer digests are 100% stable. |
| **SvelteKit Versioning** | SvelteKit defaults `kit.version.name` to `Date.now()`. Pokkum passes `SOURCE_DATE_EPOCH` to the build environment so `version.json` inside the app binary remains constant. |
| **Base Image Upstream Drift** | `pokkum.lock` records exact SHA256 digests of base images (`distroless`, `chainguard`). Subsequent builds reuse locked digests without registry queries unless `--update-base` or `pokkum base update` is run. |
| **Bun Runtime Toolchain Drift** | `bunruntime` resolver pins version, CPU variant (`standard`/`baseline`), and SHA256 checksums of release binaries. Cached executables (`~/.cache/pokkum/bun`) ensure bit-identical runtime layers. |
| **Immutable-Binary Layer Timestamps (fixed 2026-08-18, commit `1675d4c`)** | The Bun runtime layer, `pokkum-init`, and `pokkum-static` layers use a fixed `pinnedImmutableBinaryEpoch` for their tar `ModTime` and on-disk cache key — **not** `SOURCE_DATE_EPOCH`, deliberately. `SOURCE_DATE_EPOCH` defaults to the last commit's timestamp, which is correct for every layer whose *content* actually derives from the source snapshot (server/client/vendor/native/prerendered), but was wrong for these three: their bytes don't change between commits, so deriving their timestamp from a per-commit value produced a different digest on every commit — missing the local layer cache every time and defeating registry-side dedup across a fleet for a ~90MB layer. Pinning them to a fixed epoch is **more** deterministic, not less: it does not weaken bit-for-bit reproducibility, since the goal is that identical content always produces identical bytes, and these layers' content is commit-independent by construction. `layercacheutils.ComputeKey` dropped its `modTime` parameter entirely (rather than being passed a constant everywhere) so the split is structural, not a convention a future caller could accidentally violate. |
| **Go's VCS Build Stamping (fixed 2026-08-19, commit `81a6fb6`)** | Same failure class as the row above, a second and independent source of it in the identical layers: `go build` stamps `vcs.revision`/`vcs.time`/`vcs.modified` into every binary by default, so the *content* of `pokkum-init`/`pokkum-static` changed on every commit — and between a clean and dirty tree — even though their source didn't, which kept the supervisor and static-server layers churning regardless of the tar-timestamp pin directly above. Fixed with `-buildvcs=false` on the `Makefile`'s `supervisor`/`static-server` targets (which `.goreleaser.yaml`'s before-hooks also invoke) and on `blob_freshness_test.go`'s own rebuild, so the guard compares like for like. The main CLI build is deliberately left alone — `pokkum version` wants real VCS stamping. Caught only because the blob-freshness guard's own "build twice and compare" reproducibility check was revised to vary the axis that actually matters (commit-to-commit, not same-commit-twice); see `Lessons.md`. |

The Pokkum **CLI binary itself** is built reproducibly and size-optimized in every release path with the compiler build optimization flags (Roadmap "Compiler Build Optimization Flags"): `-trimpath` (strips absolute source paths, improving reproducibility and discarding path leakage) plus `-ldflags="-s -w"` (strips the DWARF symbol table / debug info) for a significant binary size reduction. This is enforced across the `Makefile` `build`/`supervisor` targets and `.goreleaser.yaml` (the official `pokkum upgrade` release pipeline); both also inject `-X main.version/commit/buildDate` so `pokkum version` carries real release metadata. `scripts/check-build-flags.sh` (run as Step 0 of `make verify`) guards against either path silently dropping the flags. SLSA L3 provenance is generated in `.github/workflows/release.yml`'s `provenance` job over GoReleaser's own published artifacts, so there is no separate build to keep in parity — the attestation covers exactly the archives the release ships.

## 4. Supervisor Contract (`/pokkum/init`)

Because Pokkum container images run without Docker or a full OS init system, the embedded `/pokkum/init` binary handles container runtime requirements:

* **Entrypoint**: `/pokkum/init -- /app/server`
* **Signal Forwarding**: Receives `SIGTERM` / `SIGINT` from Kubernetes/Docker and forwards them to `/app/server`.
* **Zombie Reaping**: Automatically reaps orphaned child processes using `unix.Wait4`.
* **Graceful Shutdown**: Waits up to `POKKUM_SHUTDOWN_TIMEOUT` (default `30s`) for `/app/server` to exit before sending `SIGKILL`.
* **Probes**: Exposes `/healthz` (supervisor status) and `/readyz` (app status) on `POKKUM_PROBE_PORT` (default `8081`).

**Compressed embedding**: The `pokkum-init` binaries are cross-compiled by `make supervisor` into the `internal/adapters/supervisor/bin` directory and embedded zstd-compressed (`.zst`) into the `pokkum` CLI, cutting the embedded footprint from ~12 MB to ~4.7 MB. `ports.SupervisorProvider.Binary` decompresses the blob on-the-fly so the bytes written to `/pokkum/init` remain the bit-identical raw ELF — image digests, layer cache keys, and supervisor version labels are unaffected.

## 5. Kubernetes Integration (`pokkum://` Resolver)

Pokkum includes a native Kubernetes resolver (`pokkum resolve` / `pokkum apply`).

### Workflow

1. In Kubernetes YAML manifests, images can be specified as:
   ```yaml
   image: pokkum://./my-app
   ```
2. Running `pokkum resolve -f manifest.yaml`:
   - Scans the YAML for `pokkum://<path>` references.
   - Automatically builds the SvelteKit app located at `./my-app`.
   - Pushes the built multi-arch image to `POKKUM_DOCKER_REPO`.
   - Injects secure `securityContext` defaults (`runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, `seccompProfile: RuntimeDefault`) unless `--no-security-context` is provided.
   - Injects default container resource `requests` (`cpu: 50m`, `memory: 64Mi`) and `limits` (`memory: 256Mi`) unless `--no-resource-defaults` is provided.
   - Appends a `PodDisruptionBudget` document (`minAvailable: 1`) unless `--no-resource-defaults` is provided, with `selector.matchLabels` scoped to the workload's own Pod-template labels (read from `spec.template.metadata.labels`, or `metadata.labels` for a bare Pod) rather than matching every Pod in the namespace. Skipped entirely — no document emitted — when no labels can be found on the workload, since a namespace-wide selector would be actively wrong rather than merely imprecise.
   - Appends a `NetworkPolicy` document restricting ingress to actual workload container ports (`containerPort`, defaulting to 3000 and 8081) and egress to expected infrastructure ports (DNS 53, HTTPS 443, OTLP 4317/4318/8889) unless `--no-network-policy` is provided. `podSelector` is scoped to the same workload labels as the PodDisruptionBudget above when available, falling back to an unscoped selector (`{}`) only when no labels can be found.
   - Injects `readinessProbe`/`livenessProbe`/`startupProbe` defaults (`httpGet` against the supervisor's `/readyz`/`/healthz` on `POKKUM_PROBE_PORT`, default `8081`) unless `--no-probe-defaults` is provided — checked independently per probe type, so a container with its own custom `livenessProbe` still gets `readinessProbe`/`startupProbe` filled in. `startupProbe` uses a 60s grace period (`failureThreshold: 30` × `periodSeconds: 2`) to protect a slow `init()` hook (DB connection setup, cache warming) from a premature liveness kill before the app finishes starting.
   - Replaces `pokkum://./my-app` with the immutable digest:
     ```yaml
     image: ghcr.io/example/my-app@sha256:123456789abcdef...
     ```
   - When the value being replaced was already a concrete image reference (not a `pokkum://` URI — i.e. this is a re-resolve of a previously-resolved manifest), records it in a `pokkum.dev/previous-image` annotation before overwriting, so a later `pokkum rollback -f manifest.yaml` (no `--to` needed) can undo this one change.
   - **Monorepo affected-detection (`--since=<git-ref>`)**: as an optimization, each `pokkum://` project's source tree is diffed against a base git ref (`internal/adapters/gitutils`). A project that has **not** changed since that ref, and for which a prior digest is known — from its manifest `pokkum.dev/current-image` annotation or from live cluster state when inspecting — **skips compilation and packaging entirely** and reuses that digest in the emitted manifest (logged `reused unaffected image reference`, surfaced via `ports.Reference.Skipped`). If no prior digest is known, or the project is affected, it is built normally, so every emitted reference is a real `repo@sha256:…`. `--since` is fail-closed: an unknown ref or a git error fails the resolve rather than silently building or silently skipping.
3. Running `pokkum apply -f manifest.yaml`:
   - Resolves all references and pipes the resulting manifest directly into `kubectl apply -f -`.

## 6. Supply Chain Security & Attestation Architecture

Pokkum embeds supply chain security directly into the image publishing lifecycle:

* **Cosign & DSSE Image Signing, wired end-to-end (`internal/adapters/cosign`, `internal/adapters/dsse`, `internal/core/pipeline.go`'s `signAndSelfVerify`)** — real as of 2026-08-18; before that date `--sign` defaulted true, validation required non-nil signers, and neither signer's `Sign()` was ever called anywhere in the pipeline, so every image shipped unsigned (see `Lessons.md`). Now: for each subject digest (the index, and every per-platform manifest — dual-published so `cosign verify` and Kyverno-style verifiers checking either target agree), Cosign signs the digest and DSSE wraps the SLSA statement, both signed with the same static private key (`--signing-key`/`POKKUM_SIGNING_KEY`, PEM text or a file path; ECDSA P-256 or Ed25519 — **no keyless/Fulcio path for signing**, only for verification elsewhere in this section), attached via `ports.Registry.AttachSignature`/`AttachAttestation` (mirroring `AttachSBOM`'s OCI 1.1 referrer-with-tag-fallback path; the `.sig`/`.att` tag convention is always written regardless of referrer support, since that's what `cosign verify`, `pokkum verify`, and remote-cache-hit verification all read by default). **Post-push self-verification is a real pipeline stage, not a test**: `Registry.FetchSignature`/`FetchAttestation` read the just-attached material back from the registry, and `CosignSigner.Verify`/`DSSESigner.Verify` cryptographically re-check it against the derived public key before the build is allowed to report `BuildResult.Signing.Signed = true` — a broken attach path fails the build rather than silently reporting success on an unsigned or unverifiable push. Without a configured key, a signing-enabled build (the default) pushes unsigned with a loud warning and records that in `BuildResult.Signing`; `--require-signed` turns a missing key or any signing/self-verification failure into a hard build failure (the CI gate). **No placeholder trust anchor exists as of 2026-08-18 (commit `a149b28`, Roadmap 2h)**: the one hardcoded placeholder public key (`cosign.DefaultPublicKeyPEM`, byte-identical to `baseimage.DefaultBaseImagePublicKeyPEM`) that used to be the shared last-resort fallback across signing, base-image, and remote-cache verification when the relevant `POKKUM_*_PUBKEY` env var was unset has been deleted rather than replaced — a trust anchor nobody owns is worse than no default. All three sites now fail closed with an error naming the exact env var/flag to set, distinguishing "no key configured" from "signature invalid." Proving this per-site found `internal/adapters/provenance/resolver.go`'s static-key path was a literal fail-open (`SignatureValid: false` with a `nil` error for a genuinely signed image — `pokkum verify`'s rebuild/comparison path had no gate on `SignatureValid` at all); it now hard-fails via `ErrStaticKeyRequired`. **Breaking change**: static-key verification with no key configured now refuses outright instead of running a no-op check; see `docs/archive/for-users.md` and `docs/Roadmap.md` 2h.
* **Escrow-Mirror Digest Enforcement (`internal/adapters/baseimage`, fixed 2026-08-18, same commit)**: a lockfile `MirrorRef` used to be pulled by its mutable `"<mirror>:sha256-<hex>"` tag with the locked `Digest` field written to `pokkum.lock` but never read back for comparison — so an attacker with push access to the project's own mirror could retarget the tag at a *different, genuinely and validly signed* upstream image (e.g. an older release with known CVEs) and every signature check would still pass (real Fulcio cert, correct identity, valid Rekor bundle, matching `docker-reference`). `Resolve` now compares the digest the mirror actually serves against the locked `Digest` immediately after the mirror pull and fails closed (naming both digests) on mismatch; first population (nothing locked yet) still works. **Breaking change**: an escrow mirror serving off-digest content now hard-fails the build.
* **SLSA Provenance Attestations (`internal/adapters/slsa`)**: Produces SLSA v1.0 predicate attestations linking the built image hash back to source git repositories and build commit digests. Includes complete M0 toolchain metadata: Go version, builder OS/architecture (`GOOS/GOARCH`), Bun binary digest, Pokkum commit ID, and `pokkum.lock` SHA256 hashes in `resolvedDependencies`.
* **DSSE Envelope Formatting (`internal/adapters/dsse`)**: Wraps attestations in Dead Simple Signing Envelopes (DSSE) before payload attachment.
* **SBOM Attachments (`internal/adapters/sbom`, `internal/adapters/registry/sbom.go`)**: Generates SPDX or CycloneDX vulnerability bills of materials and attaches them via `--sbom-attach=auto` (default): tries the OCI 1.1 Referrers API first and falls back to the legacy `.sbom` tag convention on registries that don't support referrers (ECR, older Harbor, older Artifactory). `--sbom-attach=referrer`/`=tag` force one mode explicitly, with `referrer` mode failing loudly (not silently mis-tagging) if the registry turns out not to support it.
* **OpenVEX Exemptions (`internal/ports/vex.go`, `internal/adapters/vexutils`)**: `.pokkum.yaml`'s `security.vex_exemptions` excludes specific, justified, time-boxed CVEs from `--fail-on-cve`'s threshold — every entry requires a real OpenVEX justification code, a mandatory expiry, and a mandatory owner (validated and rejected outright if incomplete or already expired). Exempted CVEs are named in the build warning, mirrored onto the image (`dev.pokkum.vex-exemptions` label / `pokkum.dev/vex-exemptions` annotation), and optionally exported as a real OpenVEX v0.2.0 JSON document via `--vex-output=<path>`.
* **Sigstore Trust-Root Refresh (`internal/adapters/sigstore`, fixed 2026-08-19)**: the embedded public-good trust root snapshot was found to be not merely stale but already rejecting genuine signatures on the newer Rekor shard (`log2025-1`, live since 2025-09-23) as forgeries — a snapshot captured before an anchor exists is byte-for-byte indistinguishable, to the operator, from a real forgery rejection. See §1's Composition Root section and `Lessons.md` for the full incident; the refresh mechanism itself (offline-by-default `Verify`, opt-in TUF client, three staleness guards) is described in §1's adapter list.
* **`pokkum verify`'s Keyless Verification — Fail-Closed on an Unconstrained Identity (`internal/adapters/provenance`)** — fixed 2026-08-18, see `Lessons.md`. The prior implementation read its expected signer identity off the certificate it was verifying (`Issuer.CommonName`, the CA's own name), so the comparison was tautological and the keyless path was dead code that failed identically for a genuine and a forged signature. `ports.ProvenanceResolverRequest` now takes `KeylessIdentity`/`PublicKeyPEM`/`TrustedRootJSON` directly from the operator (`pokkum verify --keyless-identity`/`--keyless-issuer`/`--public-key`/`--sigstore-trusted-root`); all certificate-derived identity has been deleted. `ResolveProvenance` refuses outright — before any network I/O — if the image carries keyless Sigstore material and `KeylessIdentity` is empty: an unconstrained "verify against whatever the certificate says" check would accept any Fulcio-issued certificate on earth, which is worse than not checking at all. A half-configured identity (one of the pair set, not both) also fails immediately rather than merging in a partial default.
* **Enforced Hermetic Builds (`internal/adapters/bunexec/hermetic_linux.go`)**: `--hermetic` gets real, kernel-enforced zero-IP-network-egress on Linux — an unprivileged network namespace (`CLONE_NEWNET`\|`CLONE_NEWUSER`, no root required) wraps both stages of the SvelteKit build subprocess (`Prepare`'s `bun run build`/`bun x vite build` and `Compile`'s `bun build --compile`), so a compromised build-time dependency cannot exfiltrate data or pull unpinned content regardless of what it tries. Advisory-only (env vars, clearly logged as such) on non-Linux platforms. `bunruntime.Resolver` and the SLSA provenance generator are both hermetic-aware: a cold Bun-runtime cache fails closed rather than downloading, and provenance records the real enforcement mode (`kernel-enforced-netns` vs `advisory-env-only`), not just whether `--hermetic` was requested. SSH-agent-forwarding (`$SSH_AUTH_SOCK` and friends) is closed unconditionally via env stripping (`stripHermeticSensitiveEnv`).
* **Rolling-Deploy Lineage Annotations (`internal/adapters/assetoverlay`, `--asset-overlay`)**: every image pushed with `--asset-overlay`/`--asset-overlay-from` in use is stamped with `dev.pokkum.predecessor` label / `pokkum.dev/predecessor` annotation (the digest it replaced at the same push target) and `dev.pokkum.asset-overlay-sources` label / `pokkum.dev/asset-overlay-sources` annotation (comma-joined digests of every generation actually resolved and merged). This is a deliberately Kubernetes-independent, self-bootstrapping lineage mechanism — `pokkum build` walks its own chain via repeated registry `remote.Get` calls against `<repo>:<tag>`, entirely separate from `pokkum.dev/image-history` (§5, written and read exclusively by `resolve`/`apply`/`rollback`, which `build` has no code path to parse). Only stamped when the flag is actually in use, not on every push, to avoid an unrequested registry round-trip on ordinary builds — see `docs/Roadmap.md`'s Tier 1.1 entry for the full design and a known, honestly-tracked gap with `pokkum verify`'s default rebuild-and-compare path (there is no `--rebuild` flag; rebuild is the default, opted out of via `--no-rebuild`).
* **Opt-In Mount-Namespace Isolation, `docker.sock` half (`internal/adapters/bunexec/hermetic_reexec_linux.go`, `--hermetic-mount-isolation`)**: filesystem-path Unix domain sockets (a bind-mounted `/var/run/docker.sock`) are namespaced by the *mount* namespace, not the network namespace — `CLONE_NEWNET` alone does nothing for them. Real closure needs code to run *between* namespace-unshare and `execve`, which `syscall.SysProcAttr` has no hook for — so this retargets the sandboxed subprocess to re-invoke Pokkum itself as a hidden `pokkum __hermetic-reexec` subcommand (the real target's `Path`/`Args`/`Dir`/`Env` carried through one JSON-encoded env var), already inside the new `CLONE_NEWNS` (added on top of the existing `CLONE_NEWNET`\|`CLONE_NEWUSER`) — that hidden subcommand bind-mounts an empty file over `/var/run/docker.sock`/`/run/docker.sock` if either exists, then `syscall.Exec`s into the real target (same PID throughout, so masking always completes before the untrusted process's own code runs — no TOCTOU window). **Deliberately opt-in, default off** — new, previously-unexercised raw-syscall code, unlike the already-proven `CLONE_NEWNET` mechanism; `--hermetic`'s own default behavior is unchanged for every existing user. Empirically verified in a real Linux container: a real Unix socket listener is reachable normally, still reachable under network isolation alone (proving the gap), unreachable once mount isolation runs. **Honest residual limitation**: the sandboxed process retains `CAP_SYS_ADMIN` within its own namespace (the same capability used to create the mask), so a sufficiently sophisticated dependency that specifically knows this mechanism exists could in principle `umount()` it — dropping that capability via `capset(2)` before the final exec would close this, tracked as a follow-up in `docs/Roadmap.md`, not attempted yet.

## 7. Unified Observability & OpenTelemetry Architecture

> [!NOTE]
> **Real as of 2026-08-18, both `--strategy=exe` and `--strategy=layered`** (see `docs/Roadmap.md`'s PR-5, `Lessons.md`, and `Vocabulary.md` §3a for the full investigation). The original design below assumed SvelteKit's native `kit.experimental.tracing.server`/`instrumentation.server` flags and on-disk `src/instrumentation.server.ts` auto-loading — confirmed, by reading the real vendored `@sveltejs/kit` source, to be **on-disk-config-only with no env/CLI override**, which collides with Pokkum's own Zero-Mutation Build Sandbox invariant. The mechanism actually shipped is different (two mechanisms, one per strategy, described accurately below) and neither touches SvelteKit's own config loading at all; `internal/adapters/sveltekitutils/injector.go`'s `EnableTelemetry`/`injectExperimentalFlags`/`PrepareVirtualConfig` are **not** part of the real mechanism — they predate this fix, are never invoked by anything, and are left as dead code pending a future cleanup rather than touched as part of this fix's scope. **`--strategy=exe` shipped first (2026-08-18)**, with a real scope gap caught during self-review before declaring done: the compile-entrypoint wrapper only took effect through `Compile`'s `EntrypointPath` input, which the pipeline only read for `StrategyExe` — the initial fix's negative gate check would have silently generated a real, unread wrapper file for `StrategyLayered` (Pokkum's default). Fixed to a positive per-strategy switch before shipping, with `StrategyLayered` extended to a real, working mechanism the same day rather than left as a permanent gap.

`--telemetry` compiles a real OpenTelemetry NodeSDK + OTLP trace exporter directly into the running app, via two different mechanisms depending on strategy — neither touches SvelteKit's own config-loading conventions:

* **`--strategy=exe`: Compile-Entrypoint Wrapper (`internal/adapters/sveltekitutils/telemetry.go`)**: `PrepareVirtualTelemetryEntry` writes two files under `<projectDir>/.pokkum/` (never the user's real project tree, and at fixed — not randomly-temp-dir'd — paths, so compiled output stays reproducible): `otel-bootstrap.ts` (`GenerateInstrumentationServer`'s real NodeSDK + OTLP trace exporter bootstrap) and `telemetry-entry.ts` (two static side-effect imports — the bootstrap first, the real adapter-generated entrypoint second; ES module ordering guarantees the SDK is fully started before the real application code runs). Skips cleanly (preserving user setup, starting no second SDK) when the project already has its own `src/instrumentation.server.{ts,js,mjs}`. Wired into `bunexec.Compiler.Prepare`: when enabled, `PrepareResult.EntrypointPath` is swapped to the wrapper, so `Compile`'s `bun build --compile` compiles the wrapped entrypoint without needing to know telemetry exists at all.
* **`--strategy=layered`: Packaged Preload File**: `StrategyLayered` has no compile step to wrap an import into — it packages `prep.OutputDir` directly and execs a fixed argv against the interpreted Bun runtime. `sveltekitutils.PrepareLayeredTelemetryBootstrap` instead writes `otel-bootstrap.ts` straight into `prep.OutputDir` (packaged automatically at `/app/server`, no packager layer-building change needed) and returns its path relative to that directory; `internal/adapters/packager/packager.go` then builds `[supervisor, --, bun, --preload, <absolute-path>, index.js]` instead of the unconditional `DefaultLayeredEntrypoint()`. Bun's `--preload` runs a file's side effects before the main entrypoint, exactly like the compile-entrypoint wrapper's static-import ordering achieves for `--strategy=exe`. Both mechanisms are wired via a positive `switch req.Strategy { case ports.StrategyExe: ...; case ports.StrategyLayered: ... }` in `bunexec.Compiler.Prepare` (`mem:self_review_checklist` row 11 — a negative "not static" check would silently miscover any future strategy). **A real, non-obvious Bun constraint found by running it**: `--preload`'s argument must be absolute (or `./`-prefixed) — an unprefixed relative filename is resolved as an npm package specifier and fails with `"preload not found"`. Verified end-to-end with a real `bun install` + real interpreted `bun --preload <path> index.js` run (no compile step) whose manually-created span reaches a fake OTLP collector.
* **Two real, empirically-confirmed limitations** (not assumptions — see `Lessons.md`'s 2026-08-18 entry for the investigation): no automatic HTTP/framework instrumentation, since `@opentelemetry/auto-instrumentations-node`'s require/import-hook-based patching does not take effect under Bun's runtime; and no metrics export, since combining an OTLP metrics exporter with `NodeSDK` crashes once compiled under Bun (a real Bun bundler bug producing two non-interoperable copies of a shared module in one binary — `--metrics-only` logs a runtime warning rather than silently doing nothing). Real spans, including route-templated names, require the documented `hooks.server.ts` snippet in `Vocabulary.md` §3a — a real, user-added file using stable `@opentelemetry/api`, not an automatic injection.
* **OTEL Collector Sidecar Injection (`internal/adapters/k8s`)**: When `--with-otel-sidecar` is set, `pokkum resolve` and `pokkum apply` automatically attach an OpenTelemetry Collector sidecar container specification exposing OTLP ports (`4317` gRPC, `4318` HTTP) and Prometheus scraping endpoints (`8889`/`9090`) to the generated Pod specs. Unaffected by any of the above — this operates entirely at the Kubernetes manifest level.

## 8. Layer Caching & Packaging Strategies

Pokkum supports three image compilation strategies controlled via `--strategy=layered|exe|static` (default: `layered`; `--static` is the shorthand for `--strategy=static`):

### Runtime Dimension (`--runtime=bun|node`, default `bun`, added 2026-08-19)

Orthogonal to strategy: `--runtime` picks the JavaScript runtime the `layered` strategy's `App Server Layer` executes under (`node` supports `layered` only — `exe`/`static` are Bun-specific by construction and reject `node` outright). `bun` (default) embeds a checksum-pinned Bun binary as its own layer, as described below. `node` ships **no Bun runtime layer at all** — the runtime comes from the base image instead, via a dedicated `distroless-node` preset (`gcr.io/distroless/nodejs24-debian12:nonroot`, its own `pokkum.lock` slot so it can never collide with a `bun`-targeted custom base pinned in the same project) verified with the same keyless Fulcio identity as the `distroless` preset. The entrypoint execs `/nodejs/bin/node` directly against the packaged `adapter-node` output rather than `bun --preload`/a compiled stub. This is a deliberate integrity tradeoff, stated rather than hidden: Bun's release integrity uses a single GPG-signing key plus TOFU pinning, which Pokkum verifies directly; Node's uses a rotating multi-person release-key set over `SHASUMS256.txt`, which would be materially more surface to replicate at equal strength, so Node inherits the base image's existing keyless-verification and lockfile-digest-pinning machinery instead of a Pokkum-side download-and-verify path — the Node version is whatever the pinned base digest carries, and CVE response is `pokkum base update` re-pinning. `--runtime` joins the composite remote-cache input hash, the toolchain CVE lookup, and SLSA provenance (`externalParameters.runtime`); a non-default runtime is stamped as a `dev.pokkum.runtime` label (absence means `bun`). Known open gaps: `node` + `--telemetry` is rejected outright (the layered telemetry bootstrap is Bun-specific with no Node equivalent yet), Node-core CVEs aren't queryable (distroless ships Node outside `dpkg`, invisible to both the OS-package scanner and the zero-dependency scanner's ecosystem list), and `dev`/`resolve`/`apply`/standalone `scan` have no runtime awareness yet. See `docs/Roadmap.md` 1.3.

### Multi-Layer Arch-Independent Layout (`--strategy=layered`)
The layer count and set are **not fixed** — they depend on the base image's own layer count plus whichever of the optional application layers below a given build actually produces. Run `pokkum explain <image>` against a built image for its real, per-build breakdown (digests, sizes, file counts, purposes) rather than assuming a number.

- **Base Image Layer(s)**: Distroless Linux runtime (`distroless/cc-debian12:nonroot`) or Chainguard — however many layers the upstream base itself has.
- **Bun Runtime Layer**: Pinned Bun executable (`/usr/local/bin/bun`, per platform) fetched and cached deterministically by `bunruntime.Resolver`.
- **Supervisor Layer**: Pokkum supervisor binary (`/pokkum/init`, per platform).
- **App Server Layer**: The application's server-side output, **packaged as the whole SvelteKit build directory, not a subdirectory of it** (fixed 2026-08-17 — see `Lessons.md`): a real `@sveltejs/adapter-node` build's actual entrypoint (`index.js`, plus its siblings `env.js`/`shims.js`/`handler.js`) sits alongside, not inside, the build's own `server/` subtree, and `server/`'s own chunk files reach back out to those siblings via relative imports that only resolve correctly if the original nesting is preserved. `pruneutils.PruneOptions.ExcludeDirs` excludes `client`/`vendor`/`native`/`prerendered` from this layer since each is packaged into its own layer below/separately.
- **App Client Layer** (if present): Static client assets (`/app/client/**`, architecture-independent).
- **App Vendor Layer** (if present): Split dependency JS vendor chunks (`/app/vendor/**`, architecture-independent).
- **Native Addon Layer** (if present): Native `.node` binaries and dynamic `.so` closure (`/app/native/**`, platform-specific), inspected and verified by `ClosuredNativeAdapter`.
- **Prerendered Layer** (if present): Prerendered static pages (`/app/prerendered/**`, architecture-independent). The generated `handler.js` is patched at build time to resolve this tree via the `POKKUM_PRERENDERED_DIR` env, which the packager sets to `/app/prerendered`, so prerendered pages serve from their own slim layer instead of being dropped.
- **Asset Overlay Layer** (if `--asset-overlay`/`--asset-overlay-from` resolved ≥1 prior generation): a second, separate layer also targeting `/app/client`, containing only the `_app/immutable/` (content-hashed) files carried forward from resolved prior generations — see §1.1 in `docs/Roadmap.md` for the rolling-deploy problem this closes. Built by `internal/adapters/assetoverlay` + `packager.go`'s `appendAssetOverlayLayer`; its records are folded into the attestation digest below (they cover the same `/app/client` prefix as the App Client Layer), so this is not optional bookkeeping — omitting the fold-in would make the packaged image fail `pokkum-init`'s own startup digest check.

**Layered startup attestation (hardening Option C)**: while assembling the layered layers above, the packager also computes a deterministic SHA-256 root digest over the authoritative post-processing `/app` tree (server/client/vendor/**node_modules**/native/prerendered — the exact set is `ports.AttestationRoots`, which both sides iterate; records emitted per layer by `BuildDirectoryTreeLayerWithPruning`, so pruning, precompression sidecars and stripping are already applied; shared algorithm in `internal/adapters/attestutils`) and stamps it as the `POKKUM_ATTESTATION_DIGEST` env in the image config. At container startup, `/pokkum/init` mirrors the algorithm **and the root set** (`supervisor/cmd/pokkum-init/attest.go`; it cannot import `ports`, so its list is a hand-copy that `TestAttestationRoots_MatchSupervisorMirror` parses with `go/ast` and compares against `ports.AttestationRoots` — a root added on one side only makes every layered image refuse to start, which is exactly what shipping `/app/node_modules` without updating the mirror did), re-derives the digest from the live `/app` tree before exec, and refuses to start (exit **125** — 126 is reserved for the pre-existing binary-exec-failure meaning, see §19 of `Vocabulary.md`) on mismatch — restoring the tamper-evidence property of a sealed artifact without depending on cluster-level `readOnlyRootFilesystem`. Delivering the expected value via image config env (rather than baking a file into the supervisor layer) keeps the immutable supervisor-layer cache intact. Only the layered strategy attests; exe (sealed binary) and static (no supervisor) do not.

### Single Executable Strategy (`--strategy=exe`)
Combines supervisor and standalone compiled Bun binary into a 2-layer image (`/pokkum/init` and `/app/server`).

### Static Strategy (`--strategy=static`)
Compiles a purely static site (all routes prerendered) onto a minimal libc-free `cgr.dev/chainguard/static` base. There is **no Bun runtime, no server JS, and no separate supervisor**: the embedded statically-linked `pokkum-static` binary (`ports.StaticServerProvider`) is PID 1 at `/pokkum/static`, acting as both entrypoint and probe server. It serves the `/app/client` and `/app/prerendered` trees (the `POKKUM_STATIC_ROOTS` env), performing file serving with Range requests, strong ETags, and Content-Encoding negotiation against the `.gz`/`.br`/`.zst` sidecars `precompressutils` generates. Candidate resolution for a request path is exact file, then `<rel>.html`, then a directory's `index.html` — the `.html` candidate deliberately precedes the directory-index check, and all three share one containment-checked resolver (fixed 2026-08-19: there was previously no `.html` candidate at all, so every non-root prerendered route 404'd under `adapter-static`'s default `trailingSlash: 'never'`; only `/` worked, incidentally, via the directory branch). Both `http.Server`s (content and probe) now actually bind `Addr` from the parsed `PORT`/`POKKUM_PROBE_PORT` config (fixed 2026-08-19 — previously both fell back to Go's `:http` default and raced for port 80, so every static image was unreachable on its documented ports; see `Lessons.md`). **A collapsed port configuration (`PORT == POKKUM_PROBE_PORT`) is now rejected outright at startup** (fixed 2026-08-19): the two servers are independent listeners with no mux merge between them, so collapsing them left `/healthz`/`/readyz` served by nothing while the content server kept serving pages happily — worse than refusing to start, since Kubernetes would route traffic to a container whose probes are silently dead. `Config.validate()` now fails closed (naming both env vars, `exitUsage`) before either listener is constructed, so `main.go`'s two `http.Server`s are unconditional; `pokkum build` could never have produced this configuration itself (`internal/core/model.go` rejects `Port == ProbePort` for every build request before packaging), so the check is defense-in-depth for hand-assembled configs, not a build-time gap it closes. **Conditional GET (`If-None-Match` → 304) is now implemented per RFC 9110** (fixed 2026-08-19): the server always computed and sent a strong content-hash `ETag`, and used it for `If-Range` validation, but had no request-side handling at all — a client already holding the current copy re-downloaded the full body on every request, which mattered most for prerendered HTML (deliberately `no-cache`, so revalidated on every load). The check parses `If-None-Match` as a list of entity-tags, treats a bare `*` as matching, compares weakly (the server only ever emits strong tags), and runs after the `ETag` is set but before the `Range` block, so a matching conditional returns 304 rather than 206. `If-Modified-Since` is deliberately not implemented — no `Last-Modified` is sent, and in-image mtimes are pinned to a fixed epoch for reproducibility, so a mtime-derived validator would be a *constant*, indistinguishable across genuinely different builds. Found by executing `paranoid-testing-guide.md`'s static section rather than reading it; see `Lessons.md`. **Real prerendered output is flattened from three categories, not assumed flat** (fixed 2026-08-19): `@sveltejs/adapter-static` nests prerendered output under `pages/`/`dependencies/`/`data/`, all three of which `FlattenPrerenderedOutput` merges into the packaged `/app/prerendered` tree in a fixed order, hard-failing on a cross-category path collision rather than silently overwriting — the prior flat-tree assumption meant every prerendered route 404'd despite the directory-existence check passing. `Preflight` is now strategy-aware (previously it unconditionally required a Bun/Node adapter and rejected every real `adapter-static` project before `Prepare`'s own strategy check ever ran). **Opt-in SPA fallback**: when the source project configures an `@sveltejs/adapter-static` `fallback` page, the packager stages it in the client layer and stamps `POKKUM_STATIC_FALLBACK` (an in-image path), so `pokkum-static` serves that shell with `200` on unmatched `GET`/`HEAD` routes; the file is never silently dropped (a configured-but-unemitted fallback fails the build). Because the strategy feeds `RemoteCacheInputRequest.Strategy`, static builds get their own remote-cache key space, distinct from layered/exe. Source is `@sveltejs/adapter-static` staged at `.svelte-kit/output`. Proven against a real fixture and boot test as of 2026-08-19 (`testdata/fixtures/sveltekit-static`) — the embedded `pokkum-static` binaries themselves are `go:embed`-ded from a gitignored local build directory that, until 2026-08-19, no CI job or release pipeline actually populated (`make static-server` was missing from `.goreleaser.yaml`'s hooks and from every CI workflow), so every previously-published release shipped `--strategy=static` non-functional regardless of the fixes above; see `Lessons.md`.

## 9. Diagnostic Wizards, Structured JSON Schemas & Machine-Readable DX (`v0.4`)

Pokkum provides a machine-readable developer experience tailored for CI/CD automation and developer diagnostics:

* **Structured JSON Schema Standard (`--output=json`)**: Standardizes CLI stdout responses across commands using a versioned JSON envelope (`ports.JSONEnvelope`, `schema_version: "1.0"`). Formatted by `internal/adapters/jsonutils`. Non-JSON logs are consistently routed to `stderr`.
* **Environment Preflight Diagnostics (`pokkum doctor`)**: Performs automated environment checks (`bun` binary, registry auth credentials, SvelteKit version compatibility, `.pokkumignore` sanity) with optional mechanical auto-repairs (`--fix`).
* **Project Initializer (`pokkum init`)**: Bootstraps workspace configuration and `.pokkumignore` defaults.
* **Layer Composition & Origin Tracing (`pokkum explain`, `pokkum why`, `pokkum diff`)**: Inspects container layer hierarchies, traces file origins to specific build outputs, and computes size diffs between images.
* **Interactive Container Failure Diagnostics (`internal/adapters/diagnosticsutils`)**: Automatically analyzes container crash exit codes (127 loader failures, 137 OOMKilled, port conflicts) and provides actionable remediation suggestions.

## 10. Rebuild Verification & Non-Determinism Diagnosis (`v0.5`)

Pokkum provides bit-for-bit rebuild verification and stage-level non-determinism bisection:

* **Attestation & Provenance Validation (`pokkum verify --no-rebuild`)**: Validates SLSA v1.0 attestations and Cosign signatures via `internal/adapters/provenance`, inspecting `PinnedBuildInputs` to predict toolchain compatibility.
* **Shared `layerdiff` Tar Engine (`internal/adapters/layerdiffutils`)**: Performs entry-by-entry merge-walking over uncompressed layer tarballs, diffing headers (mtime, mode, size) and SHA256 content hashes to report root cause heuristics (timestamp drift, host path embedding, unsorted maps).
* **Pipeline Stage Bisection (`pokkum repro doctor`)**: Runs static non-determinism checks (`--fast`) and dual pipeline builds in perturbed environments (`--perturb`) to pinpoint non-deterministic build steps.
* **Multi-Level Rebuild Verification (`pokkum verify`, the default mode — there is no `--rebuild` flag; pass `--no-rebuild` to skip it)**: Rebuilds the image from source in a clean temporary git worktree (`git worktree add`), compares remote vs local tarball across L1 (exact OCI index match), L2 (uncompressed `diffIDs` match), and L3 (file-level `layerdiff` report).
* **Runtime Boot Smoke Test (`tests/integration/runtime_smoke_test.go`, added 2026-08-18, commit `fc53968`)**: `TestRuntimeSmoke_LayeredStrategy_BootsAndServes` is the first test in this repo that actually boots a produced image — real `bun` build, the real embedded `pokkum-init`, a real distroless base pull, `docker load`/`run`, then polls the supervisor's `/healthz`/`/readyz` and the app's own `/`. Gated on `-short`/bun/a reachable container daemon/network, each skipping cleanly rather than failing. Covers `--strategy=layered` only — `--strategy=static` ships a different PID 1 (`pokkum-static`) with no equivalent fixture yet. Closes the specific gap that let every `--strategy=layered` image ship without a working entrypoint for this codebase's entire prior history: structural tests (layer presence, byte-for-byte determinism, golden manifests) proved the packaged bytes were correct and stable, never that the result actually runs.
* **CLI/Docs Drift as a Test Failure (`cmd/pokkum/flags_docs_test.go`/`envvar_docs_test.go`/`actionyml_test.go`, added 2026-08-18, commit `548c0e1`)**: in the spirit of `internal/architecture_test.go`'s AST-based boundary enforcement, these tests check `Vocabulary.md` against the real CLI surface in both directions — every registered flag (enumerated by constructing the real cobra tree in-process) and every `POKKUM_*` env var read by `cmd/pokkum` (via AST, not grep, so a var name mentioned only in a comment doesn't false-positive) must be documented, and `Vocabulary.md` must not document a flag/env var that doesn't exist. `action.yml`'s emitted flags are checked the same way. A documentation change that adds a nonexistent flag or drops a real one now fails `go test ./cmd/pokkum/...`.
