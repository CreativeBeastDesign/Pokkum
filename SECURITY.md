# Security Policy

Pokkum is a supply-chain security tool, so a vulnerability in Pokkum is a vulnerability in every image it builds. Reports are welcome and taken seriously.

## Reporting a Vulnerability

**Report all security vulnerabilities privately via GitHub's private vulnerability reporting.**

1. Navigate to: https://github.com/CreativeBeastDesign/pokkum/security/advisories
2. Click "Report a vulnerability" (green button, top right)
3. GitHub will create a private discussion visible only to repository maintainers

> [!IMPORTANT]
> **The repository owner must enable private vulnerability reporting in repo Settings → Security for this link to work.** If you cannot access the form, please contact the maintainer directly and let them know this setting needs to be enabled.

Do **NOT** open a public issue or discussion for any potential security problem.

## What to Include in a Report

Please provide:

- **What** — the vulnerability class (e.g., "signature verification bypass", "sandbox escape", "secret leakage", "base image not validated")
- **Where** — file path and line number if applicable, or the specific flag/feature affected
- **How to trigger it** — concrete steps to reproduce, even if theoretical
- **Impact** — what an attacker or misconfigured user could accomplish
- **Scope** — does it require special flags, custom base images, or apply to all builds?

The more specific you can be, the faster we can verify and respond.

## Scope: What We Accept

**In scope:**

- Cryptographic verification bypasses (signature, attestation, SLSA provenance)
- Base image selection or validation failures
- Sandbox/hermetic-mode escapes
- Secret or credential leakage into built images
- Trust-anchor confusion (e.g., lockfile/configuration mixing)
- Denial-of-service affecting the build pipeline

**Out of scope:**

- Vulnerabilities in upstream base images (report those to the image maintainers: distroless, chainguard, etc.)
- Vulnerabilities in the SvelteKit application itself (outside Pokkum's control)
- Vulnerabilities in transitive build dependencies (report to the dependency maintainers)
- Missing features or documentation gaps (use GitHub Issues instead)

## Response Timeline

- **Initial acknowledgment**: within 3 business days
- **Assessment**: within 7 business days
- **Coordinated disclosure plan**: agreed on with you before any public communication
- **Fix and release**: timeline depends on severity and complexity

These are targets, not guarantees. Critical issues affecting released versions will be prioritized.

## Coordinated Disclosure

Once a fix is ready:

1. A patch release will be prepared (or the fix included in the next scheduled release)
2. You will be notified before any public announcement
3. We will provide 7-14 days advance notice to downstream consumers before publishing
4. A security advisory will be posted on GitHub, crediting your report if you wish

If you discover a vulnerability during this window and someone else discloses it publicly, we will move to immediate release rather than delay.

## Supported Versions

Pokkum has tagged releases but has not had a public launch yet, so there is no established support window and no back-porting. Security fixes land on the latest release only.

| Version  | Status              | Support Ends |
| -------- | ------------------- | ------------ |
| v1.0.1   | Latest              | Current      |
| v1.0.0   | Superseded          | No updates   |
| < v1.0   | Development         | No updates   |

A real support policy will be set once there are users to support. Until then: always run the latest release.

## Verifying What You Downloaded

Release binaries are signed with Cosign and carry SLSA provenance generated by GitHub Actions. `pokkum upgrade` verifies the signature against an embedded public key by default, and `--key` overrides that key if you want to pin your own copy.

To verify the artifacts of an *image Pokkum built* — provenance, signature, base image, reproducibility — independently of Pokkum's own tooling, [`paranoid-testing-guide.md`](paranoid-testing-guide.md) §8 (SLSA provenance via `cosign`) and §9 (Cosign signature) walk through it with third-party tools rather than Pokkum's own claims.

## Questions?

If you have questions about the scope or process, ask before investing time in a report. Contact the repository maintainer via the private advisory form.
