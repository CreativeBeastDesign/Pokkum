# OpenTelemetry & Unified Metrics Architecture

> **✅ Real as of 2026-08-18, for BOTH `--strategy=exe` and `--strategy=layered`** (see `Lessons.md`'s 2026-08-18 entries and `Roadmap.md`'s PR-5 row). The 2026-08-17 investigation found the feature entirely unwired and assumed the fix was "wire up the existing SvelteKit-native-config-based generator" — that assumption was wrong: SvelteKit's `kit.experimental.tracing/instrumentation` flags and `src/instrumentation.server.ts` auto-loading are on-disk-config-only with no env/CLI override (confirmed by reading the real vendored `@sveltejs/kit` source), which collides with Pokkum's Zero-Mutation Build Sandbox invariant. The real fix uses **two different mechanisms, one per strategy** (a compile-entrypoint wrapper for `exe`, a packaged `bun --preload`'d file for `layered`, both described below) that never touch svelte.config.js or SvelteKit's native config loading at all. `injector.go`'s `EnableTelemetry`/`injectExperimentalFlags`/`PrepareVirtualConfig` (described in the old version of this memory) are **not** part of the real mechanism and remain dead code — do not assume they do anything.
>
> Two further real, empirically-confirmed limitations (compiled and run against real dependencies, not assumed): `@opentelemetry/auto-instrumentations-node`'s require/import-hook-based patching does not take effect under Bun's runtime at all (real HTTP traffic produces zero auto-instrumented spans); combining an OTLP metrics exporter with `NodeSDK` crashes once compiled via `bun build --compile` (a real Bun bundler bug, two non-interoperable copies of a shared module in one binary) — `--metrics-only` is consequently non-functional (warns at runtime).

`--telemetry` compiles a real OpenTelemetry NodeSDK + OTLP trace exporter directly into the image's entrypoint, via a compile-entrypoint wrapper — not SvelteKit's native config-loading conventions:

## Key Subsystems
- **Compile-Entrypoint Wrapper (`internal/adapters/sveltekitutils/telemetry.go`)**: `PrepareVirtualTelemetryEntry` writes `.pokkum/otel-bootstrap.ts` (`GenerateInstrumentationServer`'s real NodeSDK + OTLP trace exporter, no metrics, no auto-instrumentation — see the limitations above) and `.pokkum/telemetry-entry.ts` (two static side-effect imports: bootstrap first, the real adapter-generated entrypoint second — ES module ordering guarantees the SDK starts before the app runs). Both live under `.pokkum/`, never the user's real project tree, at fixed non-random paths so compiled output stays reproducible. `InstrumentationExists` (`src/instrumentation.server.{ts,js,mjs}`) still gates this — skip cleanly if the user has their own.
- **Wired into `bunexec.Compiler.Prepare` for BOTH strategies**: `req.Telemetry` (previously silently dropped by `pipeline.go`) is threaded through `PrepareRequest`; the gate is a positive `switch req.Strategy { case ports.StrategyExe: ...swap EntrypointPath to the wrapper...; case ports.StrategyLayered: ...write bootstrap into OutputDir... }`, deliberately NOT a negative `!req.Strategy.ApplyStatic()` check. The negative-check version was the actual first implementation and was caught as a silent-no-op-for-`StrategyLayered` bug during that fix's own self-review (`mem:self_review_checklist` row 11), not by a test or a user report — see `Lessons.md`'s 2026-08-18 entry, bug 4. `StrategyLayered`'s extension (same day, closing that exact gap) works differently since it has no compile step: `sveltekitutils.PrepareLayeredTelemetryBootstrap` writes `otel-bootstrap.ts` into `prep.OutputDir` (packaged automatically at `/app/server`) and returns its relative path via the new `PrepareResult.TelemetryPreloadRelPath`/`PackageRequest.TelemetryPreloadRelPath` fields; `internal/adapters/packager/packager.go` builds `[SupervisorPath, --, BunBinaryPath, --preload, <absolute-path>, AppServerIndexPath]` instead of the unconditional `ports.DefaultLayeredEntrypoint()` when that field is set. Real, non-obvious Bun constraint found by running it: `--preload`'s path argument must be absolute (or `./`-prefixed) — an unprefixed relative filename resolves as an npm package specifier and fails. Verified end-to-end with a real `bun install` + real interpreted `bun --preload <path> index.js` run (`TestLayeredTelemetryBootstrap_RealPreloadRun`).
- **Real spans require a real, user-added `hooks.server.ts` snippet** (`@opentelemetry/api`'s `trace.getTracer()`/`startSpan()`, using `event.route.id` for route-templated names) — documented in `Vocabulary.md` §3a, NOT automatically injected (would require either mutating the user's real file or the same on-disk-config problem above). The compile-entrypoint wrapper alone starts an SDK with nothing calling it.
- **OTEL Collector K8s Sidecar (`internal/adapters/k8s/resolver.go`)**: When `--with-otel-sidecar` is set, `pokkum resolve` and `pokkum apply` inject an OpenTelemetry Collector sidecar container spec (`4317` gRPC, `4318` HTTP, `8889` metrics) into Pod manifests. Unrelated to the above — operates purely at the K8s manifest level.
- **CLI Options (`cmd/pokkum/build.go`)**: Exposes `--telemetry`, `--no-telemetry`, `--otel-export`, `--telemetry-env`, `--trace-sample-rate`, `--metrics-only` (non-functional, see above), `--with-otel-sidecar`.
