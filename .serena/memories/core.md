# Pokkum Core Architecture

Pokkum is a Go-based zero-dependency OCI container image compiler for SvelteKit applications. It compiles multi-arch images (`linux/amd64`, `linux/arm64`) using `--strategy=layered` (N-layer layout with pinned Bun runtime by default), `--strategy=exe`, or `--strategy=static` (zero-JS static site), embedding a PID-1 supervisor (`/pokkum/init`) — and for static, the embedded PID-1 `pokkum-static` file server (`/pokkum/init`), generating native deterministic SPDX/CycloneDX SBOMs, and pushing directly to registries without a Docker daemon.

## Invariants
- Hexagonal architecture: `internal/ports` is the leaf dependency graph node; core never imports adapters.
- Bit-for-Bit reproducibility: Timestamps, tar headers, base image digests (`pokkum.lock`), and `kit.version.name` are pinned to `SOURCE_DATE_EPOCH`. Zero clock access (`time.Now()` is strictly forbidden in adapters).
- Zero-config auto-injection (Option B): `sveltekitutils.TransformViteConfig` surgically transforms `vite.config.ts/js` to inject/override the target adapter inside `sveltekit({ adapter: adapter() })` while preserving runes, compiler options, and other plugins. `bunexec.Compiler.Prepare` generates `.pokkum/<viteConfigName>` and invokes `bun x vite build --config .pokkum/<viteConfigName>` without mutating user-authored files. If `--no-inject` is set or if injection fails, it cleanly falls back to Option C (`checkEffectiveAdapter` fail-fast validation).
- Option A compiled stub launcher (implemented 2026-08-17): when `req.StubLauncher` (`--stub-launcher`, `stub_launcher` in `.pokkum.yaml`, `POKKUM_STUB_LAUNCHER`) is active, `bunruntime.Resolver` compiles a minimal entrypoint stub (`const p = "/app/server/" + "index.js"; await import(p);`) using non-foldable path expression targeting `bun-linux-x64`, `bun-linux-x64-baseline`, or `bun-linux-aarch64`, cached at `stubs/<version>/<variant>/<platform>/bun`. Custom binary bypass (`--bun-binary`) is preserved. Remote build cache input hash actively covers `StubLauncher` to guarantee cache separation. Compile-time determinism (fixed 2026-08-16, see `Lessons.md`): `compileStub` passes the entry file to `bun build --compile` as a bare relative filename (`stub-entry.ts`) with `cmd.Dir` set to its containing temp directory, not the file's absolute `os.MkdirTemp`-rooted path — `bun build --compile` embeds something derived from the entry path into the compiled binary, so the prior absolute-path invocation made the compiled stub non-deterministic across separate resolver calls for the identical `(version, variant, platform)`. Regression-guarded by `TestResolver_StubLauncher_CompileIsDeterministic` (real-bun, skip-guarded like other real-compile tests).
- Shared Registry HTTP Transport: `internal/adapters/transportutils` is the single home for the HTTP transport every registry adapter runs on; `CloneDefaultTransport(tlsConfig)` clones `remote.DefaultTransport` (preserving `ForceAttemptHTTP2`, proxy support, 50-conn idle pool) instead of bare `&http.Transport{}` literals, and `InsecureTransport()` returns the single process-wide insecure transport (lazily built once via `sync.OnceValue`), shared across `registry`, `baseimage`, and `remotecacheutils` so one-shot insecure calls pool connections instead of allocating a fresh transport per call.
- `sync.Pool` Buffer Recycling: `internal/adapters/poolutils` recycles 64KB I/O copy buffers and bounded `bytes.Buffer` instances across tarball archiving (`packager`), layer caching (`layercacheutils`), input hashing (`remotecacheutils`), and static asset pre-compression (`precompressutils`), eliminating GC allocation thrashing.
- Composite Remote OCI Input Caching & Anti-Poisoning Verification: `internal/adapters/remotecacheutils` implements `ports.RemoteCacher`, computing deterministic composite input hashes (`sha256(source + lockfile + baseDigest + bunVersion + platforms + flags)`) to skip builds in sub-100ms when matching cache tags (`<repo>:cache-<hash>`) exist in the remote registry. Cryptographically verifies Cosign static-key or Sigstore keyless signatures on cache-hit images prior to release tag promotion (`--cache-verify`, `--cache-verify-mode`, `--no-cache-verify`), safely rejecting unverified/poisoned cache entries and falling through to full source builds.
- Static Asset Pre-Compression: `internal/adapters/precompressutils` pre-compresses `/app/client` (and `/app/prerendered`) web assets within the build sandbox, inheriting `SOURCE_DATE_EPOCH` (configurable via `--no-precompress`). Format selection is per-call via `PrecompressOptions{Gzip, Brotli, Zstd bool}`: the layered strategy requests `.gz`/`.br` only — adapter-node's bundled `sirv` server never negotiates zstd, so generating `.zst` there was pure wasted build time/layer bytes (fixed 2026-08-17) — while `--strategy=static` requests all three, since `pokkum-static` genuinely serves `.zst`. Both this package's own gzip writer and `packager/layer.go`'s OCI layer gzip codepath are pinned to `github.com/klauspost/compress/gzip` (not stdlib `compress/gzip`), so compressed bytes are stable across Go toolchain versions (fixed 2026-08-17) — see `mem:self_review_checklist`.
- ELF Native Addon Stripping: `internal/adapters/striputils` automatically strips unneeded debug symbols from native `.node` addons and `.so` libraries in `/app/native` and `/app/vendor` within the build sandbox (`--no-strip`).
- Single-Pass Layer Hashing & Streaming: `internal/adapters/packager` computes uncompressed `DiffID` and compressed `Digest` simultaneously via `buildSinglePassLayer`, eliminating multiple disk read passes and compressing once per layer.
- Base Image Lockfile & Escrow: `pokkum.lock` automatically resolves and pins base image digests to guarantee reproducible builds across machines and time (`--update-base`, `--offline`, `pokkum base update`). Supports escrow mirroring (`--mirror-registry`) of base images and Cosign `.sig` tags to project registries with automatic lockfile fallback.
- Vulnerability Scanning & Reactivity Gate: `pokkum scan` performs lightweight zero-dependency targeted OS package (`dpkg/status`, `apk/db/installed`) and toolchain CVE audits against OSV.dev batch API (`internal/adapters/scannerutils`); `pokkum build` actively scans base images on resolve, logging warnings by default and actively failing on vulnerable base image digests (`--fail-on-cve`, `POKKUM_FAIL_ON_CVE`) with fail-closed incomplete scan handling (`--allow-incomplete`) and automatic audit recording in `pokkum.lock` (`last_scanned_at`, `vulnerabilities_count`, `max_severity`).
- Vendor Layer Pruning: Automatic build-time pruning (`internal/adapters/pruneutils`) strips junk files (`*.d.ts`, `*.map`, `tsconfig.json`, `README*`, tests) from `/app/vendor`, saving 15–35MB per container image without mutating local user `node_modules` (configurable via `--no-prune` and `--keep-vendor`).
- Pre-Calculated & Cached Immutable Layers: `internal/adapters/layercacheutils` caches compressed immutable layer blobs (`/usr/local/bin/bun`, `/pokkum/init`) on disk (`~/.cache/pokkum/layers/`), skipping ~100MB of tarring and gzip/zstd compression per build.
- Compressed Embedded Supervisor Binaries: `internal/adapters/supervisor` embeds the `pokkum-init` binaries zstd-compressed (`.zst`, built by `make supervisor`), shrinking the pokkum CLI by ~7.3MB (~12MB → ~4.7MB). `ports.SupervisorProvider.Binary`/`Version` decompress on-the-fly (`decodeSupervisor`, shared lazy `zstd.Decoder`); the `/pokkum/init` layer bytes remain the bit-identical raw ELF, so image digests, layer cache keys, and supervisor version labels are unchanged. A present-but-corrupt blob surfaces as `errSupervisorCorrupt` (distinct from `core.ErrSupervisorUnavailable` for an absent asset).
- Supply chain security: SLSA v1.0 provenance, Cosign digests, and DSSE envelopes are automatically generated and signed during `pokkum build` pipeline unless `--no-sign` is provided.
- Kubernetes Integration & Live History: `pokkum resolve` and `pokkum apply` resolve `pokkum://` URIs, inject hardened security defaults, and track multi-generation deployment history. `pokkum apply` performs pre-flight live cluster annotation queries (`--cluster-inspect`, `--no-cluster-inspect`) to seed deployment history across independent CLI runs on static manifest templates.
- SBOM Attachment: Native deterministic SBOMs (SPDX 2.3 / CycloneDX 1.5) are attached by default as OCI 1.1 referrers (`--sbom-attach=referrer`), with legacy `.sbom` tag fallback (`--sbom-attach=tag`). Catalogs npm packages plus, since 2026-08-17, the embedded Bun runtime as its own component (`pkg:generic/bun@<version>`, hash when known) via `SBOMRequest.BunVersion`/`BunSHA256` — `pipeline.go`'s `Build` pre-resolves Bun for `req.Platforms[0]` once, ahead of the per-platform fan-out (a deliberate cache-hit-cheap redundant resolve, not a fanOut restructure), and feeds the same value into both the SBOM and the SLSA `Toolchain.BunVersion`/`BunBinaryHash` fields — previously `BunBinaryHash` was never actually set in a real build, and `BunVersion` there used the host compiler's bun instead of the resolved embedded runtime.
- Bun Release Integrity: `bunruntime.Resolver` verifies every downloaded release archive's checksum before extraction — statically pinned SHA256 for a small set of common versions (fast path), and for any other `--bun-version`, GPG signature verification of Bun's own `SHASUMS256.txt.asc` (fetched from the GitHub release) via `github.com/ProtonMail/go-crypto/openpgp`, against an embedded release-signing public key (`Robobun <robobun@oven.sh>`). `Resolver.ReleaseKeyArmored` lets tests inject a throwaway keypair to exercise real signature verification (including tamper/wrong-signer rejection) without Bun's actual private key. Fails closed on any fetch/signature/checksum failure. **Cache-hit verification** (fixed 2026-08-17, adversarial security review): the cache-hit path is verified too, not just the download — `verifiedCacheHit` requires a matching `<binary>.sha256` digest sidecar (written by `writeCacheDigestSidecar` immediately after a download or stub-compile is cryptographically verified/hashed); a binary with no sidecar or a mismatched one is treated as a cache miss, never trusted. Cache directories are `0o700` (was `0755`); `--bun-version`/`--bun-variant` are charset/enum-validated before use in filesystem paths and URLs (previously `../`-style traversal in `--bun-version` could escape the cache root, and an unrecognized variant silently fell back to "standard"); extraction uses `os.CreateTemp` (was a deterministic `.tmp` suffix, racy under concurrent processes); the pre-verification archive read is capped at 512MB; and a truncated zip entry is caught by comparing bytes written against the entry's own recorded `UncompressedSize64`. **Known unfixed gap** (tracked in `Roadmap.md`'s backlog): `SHASUMS256.txt` entries aren't bound to the release they were published under, so a party able to substitute the fetch response could serve an older, genuinely-signed release under a newer version's name — see the doc comment on `fetchVerifiedChecksum`.
- Keyless Sigstore Base Verification: Stock presets (`distroless`/`chainguard`) use keyless Sigstore verification (Fulcio+Rekor) against embedded trust roots by default, while custom bases use static-key Cosign verification (`--base-verify-mode`).
- Hot-Reload Dev Environment: `pokkum dev` builds, loads into Docker daemon, runs, and watches source files for auto-rebuilding with interactive shell debugging (`--debug`).
- Monorepo Affected-Detection: `pokkum resolve`/`apply --since=<git-ref>` diff each `pokkum://` project tree against a base ref (`internal/adapters/gitutils`, `ports.AffectedDetector`) and skip build/packaging for an unaffected project that has a known prior digest (manifest `pokkum.dev/current-image` annotation or live cluster state), reusing that digest in the emitted manifest (`ports.Reference.Skipped`); falls through to a real build otherwise, fail-closed on bad ref/git errors.
- Static Strategy (`--strategy=static`, `--static` shorthand): compiles a purely static site (all routes prerendered) onto a minimal libc-free `cgr.dev/chainguard/static` base with **no Bun runtime, no server JS, no separate supervisor**. The embedded statically-linked `pokkum-static` binary (`internal/adapters/staticserver`, `ports.StaticServerProvider`, built by `make static-server`) is PID 1 at `/pokkum/static` and acts as both entrypoint and probe server, serving the `/app/client` and `/app/prerendered` trees named in `POKKUM_STATIC_ROOTS` (set by the packager). It does file serving with Range requests, strong ETags, and Content-Encoding negotiation against the `.gz`/`.br`/`.zst` sidecars `precompressutils` generates. Static Prepare injects `@sveltejs/adapter-static` and packages `.svelte-kit/output` staging (`client` + `prerendered`); the fan-out skips Compile and `deps.StaticServer.Binary` provides the server blob. Because the strategy feeds `RemoteCacheInputRequest.Strategy`, static builds get their own remote-cache key space. The `pokkum-static` Go binary must NOT import `internal/ports` (it duplicates the small env-literal set). SPA-fallback (implemented 2026-08-17, Option B — opt-in; see Roadmap.md): `pokkum-static` serves a runtime-configured fallback path (`POKKUM_STATIC_FALLBACK` env / `-fallback` flag, default empty) with 200 on unmatched GET/HEAD routes; default remains a plain 404. Detection is config-driven + output-verified: `sveltekitutils.StaticFallbackFilename` reads the `fallback` option from `svelte.config.js`, the static `bunexec.Prepare` verifies the exact file was emitted in the client staging (hard-fails if configured-but-not-emitted — never silently dropped), and `core` threads `PrepareResult.StaticFallbackRelPath` → `PackageRequest.StaticFallback` (`/app/client/<rel>`), which the packager stamps into the image env alongside `EnvStaticRoots`. Discovery via a once-per-process Warn log line on the first 404 while unset (no dev-marker HTML in the 404 body); tested end-to-end in `TestFixtureDrivenE2E_Static_SPAFallback`.
- Layered Startup Attestation (hardening Option C): for `--strategy=layered`, the packager computes a deterministic SHA-256 root digest over the authoritative post-processing `/app` tree (server/client/prerendered/vendor/native — records emitted by `BuildDirectoryTreeLayerWithPruning` per layer, so pruning/sidecar/strip already applied; shared algorithm in `internal/adapters/attestutils`) and stamps it as `POKKUM_ATTESTATION_DIGEST` into the image config env. `pokkum-init` mirrors the algorithm (attest.go, no `internal/ports` import) and re-derives the digest from the live `/app` tree at startup, refusing to exec (exit 126) on mismatch — tamper-evidence without depending on cluster readonly-rootfs. Delivery via image-config env (NOT baking into the supervisor layer) so the immutable supervisor-layer cache is preserved. Opt-out = override/unset the env (malformed ⇒ attestation off). Parity between the two implementations is pinned by `attestutils_test.go`'s mirrored-walk tests. Only layered attests; exe/static don't.
- Kubernetes Probe Defaults (fixed 2026-08-17): `internal/adapters/k8s/resolver.go`'s `injectContainerProbeDefaults` fills in `readinessProbe`/`livenessProbe`/`startupProbe` (httpGet against the supervisor's `/readyz`/`/healthz` on `POKKUM_PROBE_PORT` default `8081`) for pokkum-built containers that don't already define their own, checked independently per probe type. Gated by `--probe-defaults`/`--no-probe-defaults` (default on) on `resolve`/`apply`, mirroring `--resource-defaults`. Empirically verified against real `@sveltejs/adapter-node@5.5.7`/`@sveltejs/kit@2.70.2` source that `server.listen()` cannot run before `hooks.server.js`'s `init` hook resolves (handler.js's top-level `await server.init(...)` blocks index.js's import before `listen()`), so a plain TCP-connect `/readyz` (already existing) isn't racing `init()` — the roadmap's original "readiness races init" framing was wrong, corrected in `Lessons.md`. `startupProbe` is still built, for the real reason that it protects a slow `init()` from a premature `livenessProbe` kill via a 60s grace period (`failureThreshold: 30` × `periodSeconds: 2`).
- adapter-node Reverse-Proxy Contract (fixed 2026-08-17): `ports.RuntimeConfig` gained `Origin`/`ProtocolHeader`/`HostHeader`/`AddressHeader`/`XFFDepth`/`BodySizeLimit`, emitted by `pokkumEnv()` (`internal/adapters/packager/config.go`) as `ORIGIN`/`PROTOCOL_HEADER`/`HOST_HEADER`/`ADDRESS_HEADER`/`XFF_DEPTH`/`BODY_SIZE_LIMIT` only when set (each falls through to adapter-node's own default otherwise — never an empty override). Settable via `--origin`/`--protocol-header`/`--host-header`/`--address-header`/`--xff-depth`/`--body-size-limit` on `pokkum build`, or `.pokkum.yaml`'s matching `image.*` keys (flag wins). `internal/core/pipeline.go`'s `Build` logs a `Warn` at build start when `ORIGIN` is unset for layered/exe (not static, which has no adapter-node runtime) — this is the fix for the previously-unaddressed "403 Cross-site POST form submissions are forbidden" first-deploy failure behind a reverse proxy/ingress.
- Project Config Loading & Validation (`.pokkum.yaml`): `internal/adapters/config` has no generic dotted-key → `POKKUM_*` env-binding layer. Each field with an environment override reads it explicitly at its own call site; the full list is in `Vocabulary.md`'s Conventions section — most fields are config-file/flag only. `Load` uses `yaml.NewDecoder(...).KnownFields(true)` so a typo'd key (e.g. `strategey:`) is a hard parse error, not a silently-dropped field (an empty file still parses to a valid zero-value config via an `io.EOF` special-case). `pokkum config validate` (`cmd/pokkum/config.go`) validates the base config AND every named profile through one shared `validateConfigFields` helper — including `docker.repo` shape validation (`core.ValidateDockerRepo`, reusing `go-containerregistry/pkg/name.NewRepository` with `name.WeakValidation`, the same option the registry/baseimage adapters use). `BuildProfile` has a `Docker` override field (profiles can push to a different repo than the base config/other profiles), merged in `ApplyProfile`. Canonical documented example: `testdata/config/pokkum.yaml.golden`, parsed and validated end-to-end by tests in both `internal/adapters/config` and `cmd/pokkum` so it can't drift from the real schema.
- Prerendered Page Layer (layered strategy): prerendered pages are no longer dropped — they go into their own slim `/app/prerendered` layer. The generated `@sveltejs/adapter-node` `handler.js` is patched at build time (`internal/adapters/bunexec/prerendered_patch.go`) to resolve the tree from the `POKKUM_PRERENDERED_DIR` env (`/app/prerendered`), which the packager sets. The patch is version-sensitive but NOT soft: an unrecognized handler pattern (no match across the known variable-name/quoting variants) is a hard build failure, not a warn-and-continue — an unpatched handler would build and run but silently serve prerendered pages from a directory Pokkum no longer mounts, 404ing in production with nothing but a log line to explain it. As of `@sveltejs/adapter-node@5.5.7`, real bundled `build/handler.js` is a thin re-export barrel (`export { h as handler } from './server/chunks/handler-<hash>.js'`) — the pattern lives in that content-hashed chunk, not `handler.js` itself. `patchPrerenderedEnv` tries a direct match in `handler.js` first (some versions/configs may still inline it), then — on no-match — parses the re-export, resolves the chunk relative to `handler.js`'s directory, and patches that file instead (staged/written under its own name, not `handler.js`). Regression-tested against both the pre-bundling npm template (`testdata/adapter-node/{v3,v5}/handler.js`, doc-corrected 2026-08-17 to note that's what it is) and the real re-export-barrel shape (`testdata/adapter-node/bundled-real/`, `prerendered_patch_test.go`'s `RealBundledReExport`/`FollowsBundledReExport` tests) plus a real, network-built end-to-end fixture (`testdata/fixtures/sveltekit-adapter-node`, `tests/integration/layered_prerendered_e2e_test.go`).
- AppServerDir packages the whole layered-strategy build output, not a subdirectory (fixed 2026-08-17, severe pre-existing bug): `internal/core/pipeline.go`'s `AppServerDir` is `prep.OutputDir` itself — a real `@sveltejs/adapter-node` build's actual entrypoint (`index.js`, `ports.AppServerIndexPath`) sits as a *sibling* of the build's `server/` subdirectory, not inside it, and chunk files inside `server/` reach back out to siblings like `shims.js`/`env.js` via `../../`-style relative imports that only resolve correctly if the original nesting is preserved exactly — so packaging previously flattened `server/` alone into `/app/server`, and NO image ever built by this codebase actually contained its own entrypoint. `pruneutils.PruneOptions` gained `ExcludeDirs []string` (checked via `IsExcludedDir`, applied in `BuildDirectoryTreeLayerWithPruning`'s `WalkDir` callback via `filepath.SkipDir`, honored even under `NoPrune: true` since it's about avoiding cross-layer duplication, not junk) so `client`/`vendor`/`native`/`prerendered` — each already packaged into its own layer — aren't duplicated into `/app/server` now that the whole build output is walked. Verified by extracting a real built layer from an OCI tarball and running `bun index.js` against it directly (see `mem:self_review_checklist` row 17, added by this incident).
- Zero-Config Injection `__dirname`/`import.meta.url` correctness (fixed 2026-08-17, PB-5): `sveltekitutils.PrepareVirtualViteConfig`'s virtual config lives one directory deeper than the real `vite.config.ts` (`<projectDir>/.pokkum/`); confirmed empirically with a real Bun invocation that Bun injects `__dirname`/`__filename` as ambient globals even under ESM, so the near-universal `path.resolve(__dirname, './src/lib')` pattern (used to build `resolve.alias`) silently resolved into `.pokkum/` before this fix. New `shimDirnameAndImportMetaURL` prepends module-scoped `const __dirname`/`const __filename` declarations pointing at the real config's real path (a top-level `const` shadows the ambient global for every reference in that module) and textually substitutes every literal `import.meta.url` token with the real config's precomputed `file://` URL (can't be shadowed the same way — it's a read-only meta property) — same textual-substitution philosophy as the file's existing `rewriteRelativeImportSpecifiers`, not a JS/TS parser.
- `$env/static/*` build-time-baking detection (implemented 2026-08-17, PB-3): `sveltekitutils.DetectStaticEnvBindings` scans a project's `src/` tree (`.ts`/`.js`/`.svelte`/`.mts`/`.mjs`, skipping `node_modules`/`.svelte-kit`/`.pokkum`/`.git`/`build`/`dist`) for `$env/static/public`/`$env/static/private` imports, extracting named bindings (`import type` correctly excluded — erased at compile time; `$env/dynamic/*` correctly excluded — read at runtime, never baked). Wired behind a new `ports.EnvBakeDetector` port (`internal/adapters/envbake`, wrapping the sveltekitutils scan) rather than importing the utility package directly from `internal/core` — the hexagonal boundary rule (`internal/core` imports `internal/ports` + stdlib only) applies to utility packages too, not just concrete adapters; this was caught by `internal/architecture_test.go` before landing. `core.Build` calls it unconditionally for every strategy (SvelteKit's Vite plugin resolves the virtual module during the shared build step, not per-adapter), `Warn`s naming the exact bindings, and stamps them as `req.Runtime.EnvBaked` → `pokkum.dev/env-baked` manifest annotation (mirrored through `mergeLabels`/`imageAnnotations` exactly like `pokkum.dev/required-env`). Known limitation, matching the item's own framing: a source-level heuristic, not data-flow analysis — doesn't follow re-exports or dynamic import specifiers.
- Real Layer Introspection (`pokkum explain` / `explain why` / `explain diff`, fixed 2026-08-17): all three read real OCI data end-to-end — no fabricated fallback anywhere in the success path; an unreadable value renders an explicit `"(... unknown)"` marker (byte counts/digests are never negative/empty for real, so the marker can't be mistaken for a genuine answer). `cmd/pokkum/explain.go`'s `resolveImage` fetches a registry ref or local `.tar`, resolving a multi-arch index to one platform's child the same way `baseimage/resolver.go`'s `selectPlatform` does (`--platform`, default host platform) — but `ExplainOutput.Platform` is always read back off the resolved image's own `ConfigFile()` (`imageConfigPlatform`), never the requested flag directly, since a local `.tar` or a remote non-index ref never actually consult `--platform` to select anything and echoing the flag there printed an unverified value (a real bug caught by manual smoke-testing, not by any unit test — see `Lessons.md`). Layer **purpose** comes from `ConfigFile().History` — every layer Pokkum appends already carries a real `CreatedBy: "pokkum: add <path>"` entry (`packager.go`) — via `layerPurposes`, which cross-checks the `EmptyLayer`-filtered `History` count against `RootFS.DiffIDs` length (both must agree with the real layer count) before trusting the mapping; on disagreement it falls back to `"(no history metadata)"` for every index rather than risk a length-preserving misalignment silently shifting purposes to the wrong layer. **No static layer-count anywhere** — this is also the real PR-9 fix (the layered strategy's actual count varies per build: bun + supervisor + server + whichever of client/vendor/native/prerendered a given build produced, on top of however many layers the base image itself has), so every doc site that claimed a fixed `"5-layer"`/`"8-layer"` count now points at `pokkum explain` instead. `explain why <image> <file-path>` (new: `<image>` is now a required arg — the stub never took one) walks real layers last-to-first via new `layerdiffutils.ListTarPaths`/`TarEntry` (whiteout/opaque-whiteout aware): found in a layer, deleted via that layer's per-file whiteout, made ambiguous by an opaque-whiteout resetting its directory (an earlier "found" would be actively wrong there, not just incomplete — the opaque case is checked, not just the per-file one), or never present. `explain diff <image1> <image2>` short-circuits on matching manifest digests, else walks real per-layer digests and, where they differ, real per-file changes via `layerdiffutils.CompareTarStreams` (sorted before output — its own entries come from Go map iteration and are not order-stable; capped at 20 changes/layer with an explicit `"+N more"` line, never a silent drop). Every `Uncompressed()`/`Compressed()` reader in `why`/`diff`'s per-layer loops is closed explicitly right after use, not via `defer` inside the loop. Real command paths are `pokkum explain why`/`pokkum explain diff` (subcommands of `explain`, not top-level) — docs previously claimed top-level `pokkum why`/`pokkum diff`, a pre-existing drift fixed alongside this.
