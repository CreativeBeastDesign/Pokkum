# Self-Review Checklist

A concise, invariant-style checklist run against every non-trivial code diff before declaring it complete, as part of the verification protocol in `mem:task_completion`. Unlike `Lessons.md` (an append-only, chronological incident log kept in the repo root), this memory holds only the *currently-active, distilled* rules and is edited in place, not appended to — that's why it lives in Serena rather than the log itself.

Shared across every agent/harness working this codebase (each has Serena access) — this is the one source of truth for the checklist; do not fork a duplicate copy into a harness-specific instruction file.

## How to use

1. After a diff is otherwise ready (tests green, `make verify` passing per `mem:task_completion`), walk every row below against the actual diff lines — not from memory of having read it once.
2. If a row doesn't apply, say so explicitly ("N/A: no concurrent dispatch in this diff") rather than skipping it silently.
3. If a bug is found during this pass, log the root cause and preventative rule in `Lessons.md` (repo root), then come back and close the loop here (see Maintenance rule below).

## Checklist

| # | Check | How to verify |
|---|-------|----------------|
| 1 | Fan-out error paths — prefer structurally impossible over carefully avoided | For every `errgroup.Group`, `sync.WaitGroup`, or bare `go func()` touched by the diff: grep for every `return`/`continue`/`break` sitting between the dispatch call and its corresponding `Wait()`/`Done()`. Each one is a leak candidate until you can point to why it's safe. **When you find or fix one, prefer a structural fix over a guard**: if the fallible decisions that can error (validation, skip/reuse checks) can be fully separated from the dispatch loop — computed in an earlier pass with zero goroutines in flight, so no fallible call is ever positioned between a dispatch and its `Wait()` — do that separation instead of just adding a careful early-return. A guard only holds as long as every future edit happens to preserve an invariant nothing in the code enforces; this exact bug recurred in `internal/adapters/k8s/resolver.go`'s fan-out (see Origin note) after being fixed once with a guard, and was only fixed for good once the loop was restructured into a validate-then-dispatch two-pass shape that makes the leak unreachable by construction. |
| 2 | Resource cleanup on every branch | For every `os.File`, `io.Reader`/`io.Closer`, network conn, or lock acquired in the diff: trace every return path, including new early-return branches just added, and confirm cleanup runs on each — not just the happy path. |
| 3 | Multi-item collection logic | If the diff processes a collection (map, slice, multi-document stream), does at least one test use ≥2 items with *differing* content/outcome? Single-item or all-identical fixtures hide item-interaction bugs. |
| 4 | Non-first-item failure injection | For every new error path inside a loop or fan-out, does a test trigger the error on a *non-first* item, not just the first/only one? A single-item error test can pass while a real multi-item failure leaks resources. **This row and row 1 have already failed to prevent a recurrence once** (see Origin note) — a guard-shaped fix passed this exact check at the time it was written, then regressed when a later edit reintroduced interleaved dispatch-and-validate logic that nothing forced a re-check against. Treat a passing test here as necessary, not sufficient: also ask whether the fix could be made structural (row 1) so the next edit can't silently reintroduce the interleaving in the first place. |
| 5 | Ordering / determinism — of *selection*, not just of output | Are map iterations, directory traversals, and concurrently-produced results consumed in an explicitly sorted or otherwise deterministic order (bit-for-bit reproducibility invariant, `mem:core`)? **A sorted output is not evidence, and this row previously read as though it were** (2026-08-22): for every `for k, v := range someMap` in the diff whose body writes into a keyed collection (`seen[name] = ...`, `entries[name] = ...`, or an append later collapsed by key), ask what happens when two iterations resolve to the *same* key. If either can win, the winner is random — and downstream sorting produces a stably-ordered list of unstable contents, which reads exactly like a fix and passes every ordering assertion. Every npm-family lockfile parser in this repo had this defect simultaneously: one package name legitimately appears at several versions (a hoisted copy plus nested ones), and ranging over the map let Go pick, so six builds of unchanged source emitted six different SBOM digests and package counts between 9 and 15. Fix at the collision — sorted iteration **plus an explicit, documented precedence rule** for which duplicate wins — not at the output. Prove it with a duplicate-key fixture run enough times that map-order randomness cannot pass by luck (a two-entry collision passes a single run ~50% of the time); assert both stability *and* that the semantically correct entry won. |
| 6 | Clock / timestamp access | Does the diff introduce any `time.Now()` or system clock read outside `req.SourceDateEpoch`? |
| 7 | Go version regression | Does the diff touch `go.mod`'s `go` directive or any `go-version:` line in `.github/workflows/*.yml`? If so, `git diff` those exact lines and confirm the version only holds steady or increases — never decreases. |
| 9 | Runtime-vs-construction validation | Does the diff rely on a precondition that can change at runtime (a file's existence/type, openness) but only validate it once at construction/setup? If so, the code path must re-check the precondition at the point of use and degrade to the normal-miss path, never escalate to 5xx or serve stale state. |
| 8 | golangci-lint clean | Has `make lint` (which runs the pinned v2 linter via `go run`, and is folded into `make verify`) actually been run against this diff — not just `go vet`? **Check the output says how many issues it found, not merely that the command exited 0**: a bare `golangci-lint` from PATH may be a v1 binary that cannot load the v2-schema config, or one built with an older Go than `go.mod` targets, in which case it exits non-zero without linting a single file — and in CI that failure silently skipped every verification step behind it for six consecutive runs (see row 47). `gofmt`/`go vet`/`go test` all pass on findings golangci-lint alone catches (`errcheck`, `staticcheck`, ...); see the Origin note below. |
| 10 | Base-vs-profile config field parity — validation AND merge | If the diff adds, removes, or changes a `ports.ImageConfig`/`ports.ProjectConfig` field: (a) does `cmd/pokkum/config.go`'s `runConfigValidate` (or the shared `validateConfigFields` helper) apply the same check to it via the per-profile iteration over `cfg.Profiles`, not just the base-config call? (b) separately — a distinct function, a distinct miss — does `internal/adapters/config/config.go`'s `ApplyProfile` include an explicit `if profile.Image.X != zero { merged.Image.X = profile.Image.X }` line for it? `ApplyProfile` is hand-written per-field, not reflection-based, so a new struct field is silently invisible to `--profile <name>` (parses fine, validates fine, then discarded) unless a matching merge line is added — this is a *second*, independent place the same new field can be forgotten, not covered by fixing (a) alone. Grep both `runConfigValidate` and `ApplyProfile` for the new field name; both must appear, or say explicitly which one legitimately doesn't apply and why. |
| 11 | Strategy-gated logic scoped to the right strategy | For any `if`/`switch`/`else` in `internal/adapters/bunexec`, `internal/adapters/packager`, or `internal/core/pipeline.go` that branches on `req.Strategy`/`ports.BuildStrategy`: is an `else`/`default` arm actually correct for *every* strategy it covers, or was it written assuming only one specific strategy would ever reach it? A negative check (`!= StrategyX`, "not static") is not the same as a positive check (`== StrategyY`) — the former silently includes every future or existing strategy nobody thought about when the branch was written. Trace which strategies actually execute the branch and confirm each one's real toolchain output matches what the branch assumes. |
| 12 | Fixture fidelity to the real consumed artifact — and its provenance claim | For a fixture/mock claiming to be "real" (sourced from an actual upstream package, a real tool run, a real npm package, etc.): is it sourced from the *exact pipeline stage* the code under test actually reads — or from an earlier stage (e.g. a package's source template) that merely resembles the final artifact? A fake-bun/fake-tool test harness's fixture content must model what the real tool would emit for that exact code path, not just whatever satisfies the current implementation — check this by asking "would running the real tool right now actually produce this?", not "does this fixture make the test pass?". A doc comment asserting "captured verbatim from a real run of X" is itself a claim to verify, not evidence on its own — especially for a sub-agent-authored fixture — so if the real command is runnable in this environment, actually re-run it and diff the output before trusting the comment. **This also covers a test double's capability configuration, not just its content**: for a test claiming to exercise a capability-gated code path (an opt-in registry/API feature, a feature flag, a protocol version), check that the mock/fake/in-process server actually has that capability turned on — a double that defaults to the less-capable configuration can make an "advanced path works" test pass by accident via whatever fallback exists for the less-capable case, silently turning a positive test into a no-op (see `Lessons.md`'s 2026-08-17 `--sbom-attach=referrer` entry, where the in-process test registry's OCI 1.1 referrers support was off by default). **This recurred 2026-08-19** in a brand-new package (`internal/adapters/bunexec`'s static-strategy prerendered handling): a synthetic `staticFixtureCompiler` fabricated a flat `prerendered/index.html` tree — the same wrong assumption the production flattening code made — instead of the real nested `prerendered/pages/` shape `@sveltejs/adapter-static` actually emits, so the one test exercising it agreed with the bug rather than catching it. This row's coverage is not a one-time closed item per package; re-apply it whenever a new adapter/strategy integration gains its own synthetic fixture, not just the ones already named in this Origin section. **Extended 2026-08-21:** for a boot/e2e test whose value is that it exercises the REAL artifact, enumerate what the fixture makes structurally *impossible* before trusting green — such a test inherits its coverage from its input. `testdata/fixtures/sveltekit-adapter-node` declares every package under `devDependencies` and no `dependencies` at all, so the only test in the repo that boots a produced image passed throughout an outage in which every layered image exited 125: with no production dependencies there was no `/app/node_modules` layer, so the drifted attestation root sets agreed trivially. If the diff's subject is a category of shipped content (production dependencies, prerendered output, native modules), confirm the fixture actually contains that category, and assert the coverage rather than only the outcome — a floor read from the produced artifact (member counts under each in-image prefix, a runtime-reported file count) fails when the fixture silently narrows what "it booted" is a claim about. |
| 13 | Caller-chain coverage for a same-diff fix | If the diff fixes function B, and B is called by A before some other check in A runs (or by C after B), does at least one test exercise A (or C) end-to-end with the same real-world input the fix targets — not just B in isolation? A thoroughly unit-tested fix can still leave the real call chain broken if a sibling check earlier or later in the same chain was never revisited. Grep the fixed function's callers; if any of them do their own independent validation before/after calling it, that caller needs its own test with the fix's target input, not just the fixed function. **This recurred 2026-08-19**: `internal/adapters/bunexec/compiler.go`'s `Preflight` — called by `core.Build` ahead of `Prepare` in the exact same real call chain this row was written about — hard-required a bun/node adapter and had no `Strategy` field to consult, rejecting every correctly-configured `adapter-static` project before `Prepare`'s own strategy-aware check ran. The row already named this function pairing from a prior incident and did not by itself prevent the second occurrence, because nothing forced re-running its discipline when a new `ports.BuildStrategy` value was added. Treat this row as needing re-application on every new strategy/enum value added to a dispatch a sibling function in the same chain also branches on, not as permanently satisfied once the named functions were fixed. |
| 14 | Auto-fix/auto-inject features need a fixture the feature is meant to fix | For a diff touching a feature whose entire point is to correct, inject, or paper over a misconfiguration (zero-config injection, auto-repair, `--fix` flags, defaulting logic): does at least one test fixture start in the *broken* state the feature exists to handle, not only already-correct fixtures? A fixture that's already correct can pass every assertion whether or not the feature under test does anything at all — it structurally cannot tell you the feature works. |
| 15 | External compiler/tool output determinism, and unverified non-determinism hypotheses | For any diff invoking an external compiler/tool (`exec.Command`) whose output becomes a shipped artifact (embedded binary, layer content): if any argument or `cmd.Dir` is an absolute path that varies per invocation (an `os.MkdirTemp` directory, PID, timestamp), does the artifact's byte-identity depend on that path? Verify empirically — run the exact production invocation shape twice with only that one input varied and diff the output — rather than shipping a fix based on a plausible-sounding but unverified mechanism (linker build-id, ASLR, embedded timestamps). A repro that changes two things at once (e.g. both the output filename and the source path) can implicate the wrong mechanism entirely; isolate one variable at a time before designing the fix. |
| 16 | Feature reality check before marking an item `status: shipped`, and before *starting* a fix for a roadmap item's problem statement; test-shape vs. test-substance | Before setting an item's `status: shipped` in `docs/roadmap/<area>.yaml` — and before trusting an existing status that already looks satisfied — grep the implementing file for the I/O primitive the feature's description necessarily requires: a command claiming to inspect a remote image must reference `remote.`/`Fetch`/a tar reader somewhere; a claimed endpoint must register a handler for that exact path; a claimed emitted field must contain that field's literal name in the producing code. Absence of the required primitive is proof of absence of the feature, full stop — a passing test is not counter-evidence if the test only asserts output *shape* (correct JSON keys, correct exit code) rather than asserting the output was *derived from real input* (e.g. a digest that changes when the underlying image changes). For a feature named with "X and Y" (two halves in one description, one flag, or one row): verify each half independently: it is common for one half to be real and the other a stub, and a test exercising only the real half will pass cleanly while the row still overclaims. **The mirror case, at the start rather than the end of a fix:** an *open* roadmap item's `problem` field is also an unverified claim — if it says "`--some-flag` triggers X," grep `cmd/pokkum/*.go`'s actual flag registrations for that exact flag name before starting. A Go struct field or port request parameter existing is not evidence a CLI flag reaches it; the field can be real and correctly consumed while the flag that's supposed to set it was never wired at all, making the "fix" invisible from the CLI until that's caught too (see `Lessons.md`'s 2026-08-17 `--bun-version` entry). **Same discipline applies to a documented invocation path, not just a documented feature or flag**: when rewriting or verifying a command's docs, run `--help` (or `go run ./cmd/pokkum <claimed-path> --help`) against the actual built binary and diff it against what the docs claim the command line looks like — a subcommand nested under a different parent than the docs describe (`pokkum explain why` documented as top-level `pokkum why`) is the same class of unverified claim as a fabricated field, just cheaper to check (see `Lessons.md`'s 2026-08-17 `pokkum why`/`pokkum diff` entry). **Also check field-level provenance within an otherwise-real feature**: for each field in a new "reads real data" command's output, does it come from the *resolved/verified* result, or does it just echo an *input parameter* (a flag, a request field) that only some of the function's code paths actually use to produce that result? An echoed-but-unverified input looks identical to a real observation in every unit test that happens to pass a value already consistent with the fixture — it only diverges against a real input crafted to disagree, which is exactly why a manual smoke test against a real build (not just synthetic fixtures) caught this once already (see `Lessons.md`'s 2026-08-17 `pokkum explain`'s `Platform` field entry). **Extended 2026-08-21:** an item's `recommendation` can name a *validation method* — "validated against a corpus of real minified bundles", "benchmarked against", "checked against the upstream spec". That method is acceptance criteria, not advice: do not set `status: shipped` until it has been run and its output recorded in the item's `decision`, with corpus size and composition stated. A commit message asserting a trade-off is acceptable is not the artefact; the measurement is. And a code change that ships while its item stays `open` is the worst of both — grep recent commit subjects for `closes <item-id>` against items still marked `open` before starting one, because the fix may already be in `main` with only the evidence missing. |
| 16b | A dependency required-and-validated as non-nil is not evidence it is ever called | For any diff wiring in a signer/verifier/other side-effecting dependency that `Validate()` or an equivalent constructor-time check requires to be present: grep the actual execution path (not the validation path) for a call to its real method (`.Sign(`, `.Verify(`, `.Attach(`, etc.). A dependency can be required, checked for nilness, and threaded through every constructor while the one line that actually invokes it is missing entirely — this reads identical from the outside (no error, clean build) to a working implementation, and is indistinguishable from success in every test that only asserts the dependency was *constructed*, not *invoked*. This is a specific, sharper instance of row 16's "grep for the required I/O primitive" discipline — added as its own row after the exact failure recurred on the exact category row 16 was written to catch (see `Lessons.md`'s 2026-08-18 image-signing entry: `--sign` defaulted true, `CosignSigner`/`DSSESigner` were required non-nil, and neither's `Sign()` was ever called anywhere in the pipeline). |
| 24 | A security check's expected value must originate outside the artifact being checked | For every comparison inside a verification/signature/attestation path (`==`, `strings.Contains`, a certificate field read, a claimed-identity lookup): trace where the value being compared *against* (the expectation) came from. If it was read off the same certificate, signature, payload, or artifact the check exists to validate — rather than from a flag, a config file, or an operator-chosen default tied to a known publisher — the check is tautological: it will pass for a genuine artifact and an adversarially crafted one identically, because the artifact is grading its own homework. This is easy to miss because the code often *looks* like a real check (a real field is read, a real comparison runs) and a test asserting only `valid == true`/`valid == false` on today's fixture cannot distinguish a self-referential check from a real one — both return the same boolean on the one fixture available. When fixing such a check, audit the fix itself for the same defect one level up: does comparing the corrected field against *itself* rather than an external expectation make the check trivially satisfiable by anything the artifact carries? (See `Lessons.md`'s 2026-08-18 keyless-identity entry: the naive fix — reading the real OIDC issuer extension and comparing it to itself — would have made any Fulcio-issued certificate on earth verify, which is worse than the dead-code bug it replaced.) A dead security check and a universally-passing one are indistinguishable from the outside and from most test suites; both require tracing every comparison's operands back to their source, not just confirming a comparison exists. |
| 25 | A control whose absence is indistinguishable from success will eventually be absent | If a diff adds a security control (a signature, an attestation, an integrity check) whose entire job is to make some later consumer trust an artifact: does anything verify, immediately and within the same operation, that the control was actually applied and is actually retrievable/checkable by that later consumer — or does "the step ran with no error" stand in for "the control now genuinely protects this artifact"? A control that can silently no-op (a signer that's never called, a check that's skipped on one branch, a flag that's parsed but never read) looks byte-for-byte identical to one that worked, in every log line and every green test, until a real consumer downstream tries to rely on it and fails — often much later, and far from the code that dropped it. The fix is architectural, not just a test: have the producing step read back what it just wrote from the real destination (the registry, the filesystem, wherever the consumer will actually look) and cryptographically/structurally re-verify it before reporting success, so "reported signed" becomes impossible to reach by any path that didn't genuinely produce a fetchable, verifiable artifact. See `Lessons.md`'s 2026-08-18 image-signing entry: `core.signAndSelfVerify` now fetches the just-attached signature and attestation back from the registry and re-verifies them cryptographically before the build is allowed to report `Signed: true` — the same discipline this row asks for, applied as the actual fix, not just the review comment. Distinct from row 25's sibling, row 16b: 16b is about *detecting* a dependency that's never called; this row is about *designing the control so its own absence becomes loud* rather than relying on review to keep catching it. |
| 26 | Text-scanning bounded by a fixed token/line/size constant needs a repro against realistic *generated* input, and "scan step errored" must be distinguished from "scan step found nothing" | For any diff that scans file content line-by-line or in fixed chunks (`bufio.Scanner`, a fixed-size read buffer, a regex applied per-line): what is the actual size/length ceiling, and is there a test that constructs input at or beyond it using *realistic generated content* — a real minified/bundled file, not hand-written fixtures, which structurally cannot produce a pathological single-line-is-the-whole-file shape? `bufio.Scanner`'s default 64KB token limit is the single most common trap in Go, and it fails silently unless explicitly checked: it returns `bufio.ErrTooLong` from `Scan()`, which a caller that treats "any error from the scan step" as "skip this file / report clean" converts into a false-negative that looks identical to genuinely-scanned-and-clean. Separately, check whether a regex/pattern match loop stops after the first match per line/file (`FindStringIndex`+`break`) rather than finding all matches (`FindAllStringIndex`) — on realistic minified content where an entire file can be one line, this hides every finding after the first regardless of the size-limit bug. Both failure modes must surface as a distinct, typed result ("could not scan this file," e.g. a skip list plus a dedicated sentinel error) rather than being silently folded into "nothing found here" — the two are not the same claim, and a security-relevant scanner must never conflate them. See `Lessons.md`'s 2026-08-18 secretguard entry. |
| 17 | Packaged output must actually execute, not just exist with the right bytes | For any change to what gets packaged into a container layer (`internal/adapters/packager/*`, `internal/core/pipeline.go`'s `pkgReq.*Dir` assignments, anything touching `AppServerDir`/`AppClientDir`/etc.): extract the actual built layer from a real end-to-end build (a real fixture, not a synthetic mock) and run its entrypoint (or the specific artifact) directly — `tar -xzf` the layer blob, `cd` into it, execute it, confirm it actually starts/serves. Tar-member presence, byte-for-byte determinism, and digest stability tests (which this codebase has many of) prove none of this — a file can be present, byte-correct, and still fail to run once extracted into its real sibling directory structure (e.g. a relative import that assumed a different nesting). If the only test coverage for a packaging change is a synthetic mock's directory shape, confirm that mock's shape was itself checked against a real build of the real upstream tool (adapter-node, Bun, etc.) — a mock can encode the same wrong assumption as the bug it's meant to catch. **Extended 2026-08-21:** "executes" includes clearing the image's own startup gates, not just the app's entrypoint logic — a layered image whose startup attestation does not verify exits 125 before the child ever runs, and every byte-level and tar-member assertion still passes. If the diff changes WHICH paths are packaged (a new layer, a new in-image prefix), the only check that covers this is booting a real built image and asserting it reaches "child started"; a History entry naming the layer, and a digest oracle built from the packager's own `req.App*Dir` table, both agree with the bug. |

| 27 | A new branch must be observed executing, and a capability must cover the inputs it is *for* | Two halves, both from 2026-08-22. **(a) Reach:** if the diff adds a branch, assert an effect that exists *only inside* it — by driving the real entry point, not the helper it calls. Reading the condition, or logging the values that feed it, proves nothing: an `else if` written under a long or deeply nested block chains to whatever `if` actually precedes it, not the one it lines up with visually, and Go, `gofmt`, `go vet`, `make lint` and all five verification steps stay clean while the branch never runs once. Prefer a standalone `if` with an explicit condition over an `else if` whenever the preceding block is long enough that the binding is not visible at a glance. **(b) Scope:** if the diff implements a capability *inside* a conditional path that exists for some other reason (an injection, an auto-repair, a fallback, a migration), write down which inputs reach that path and confirm that set is the set the capability is meant to serve. A capability that piggybacks on a fix-up path silently inherits "the input was broken" as its trigger — often the exact complement of what it should cover. This shipped for weeks: the `kit.version.name` reproducibility pin lived in the adapter-injection path, so only *misconfigured* projects built reproducibly, and correctly configured ones silently did not — the failure sits in the case everyone assumes is the safe one. Pair with row 14: a fixture that starts in the broken state exercises the fix-up path, and therefore cannot detect that the capability is missing for correct input. |

| 18 | Security control scope — every untrusted-execution site, not just the one named | When adding a security control that wraps subprocess execution (a sandbox, a network restriction, a privilege drop): grep the whole package for every `exec.Command`/`exec.CommandContext` call, not just the one a roadmap item's line reference or bug description points at, and ask "does the same untrusted-code-execution risk this control is closing also apply here" for each one. A multi-stage pipeline is exactly where a partial fix hides — the fixed stage's tests pass cleanly, giving a false sense of completeness while a later stage runs the same untrusted input with zero protection. Verify the control actually blocks the thing it claims to, empirically (a real listener/real probe the sandboxed process is proven unable to reach), for every site, not just one representative site. |

| 19 | Cross-process test state — an in-process variable override does not reach a separately-compiled subprocess | If a test needs to exercise code that runs as a genuinely different OS process (a `/proc/self/exe` reexec helper, a hidden CLI subcommand, anything invoked via `os.Executable()` rather than called as a plain function) — check that whatever the test overrides to control that code's behavior actually crosses the process boundary. Overriding an in-process package variable only affects the *test binary's own* compiled copy of it; a separately-built binary (even from the identical source) has its own independent copy, unaffected by the test's mutation. Only environment variables, files, sockets, or other genuinely cross-process channels reach the other process. If the test passed anyway, ask why — a false pass here looks identical to a real one (no error, just the wrong path silently taken), which is what makes it dangerous. |

| 20 | Extract-then-repackage path round-trip fidelity | For any diff that extracts content from a packaged location (a tar entry under some prefix) into a scratch directory later re-packaged under a prefix (same or different) — not a plain file copy, an extract → intermediate-directory → repackage round-trip: does at least one test assert the *exact* relative path written to the intermediate directory, and ideally the *final, fully-reconstructed* in-image/consumer-facing path — not just "content landed somewhere under the scratch dir with the right bytes"? A test that only checks reachable-content-with-right-bytes at an unasserted sub-path can pass even when a prefix-stripping bug silently drops or adds a path segment, because the wrong sub-path still satisfies "some file, correct bytes, under the directory." Also check that the fixture actually models the real nested directory shape the feature operates on (e.g. `_app/immutable/chunks/...`, not a flattened single-level filename) — a flattened fixture used for unrelated convenience (a test helper that doesn't `MkdirAll` nested paths) structurally cannot expose this bug regardless of how carefully digests are checked. |

| 21 | Cross-layer record aggregation must dedupe by final path, matching real layer-squash semantics | If a diff can produce TWO OCI layers that legitimately target the same in-image path/prefix (e.g. two separate `mutate.Addendum`s both rooted at the same directory), and their per-file records feed one aggregate digest/manifest/index computed by concatenating without dedup (grep for `RootDigest`, or any `append(records, moreRecords...)` pattern feeding a hash): does at least one test use a fixture where BOTH layers contain the SAME relative path (with different bytes, so a wrong answer is detectable), and assert the aggregate matches an oracle that also dedupes — modeling the real, single, layer-squashed filesystem a container actually sees, not a bag of per-layer records? A test whose fixture only uses non-overlapping paths across the two layers cannot expose double-counting, and an oracle that mirrors the same non-dedup logic as the code under test will agree with a bug instead of catching it. Also verify addenda/record ordering: OCI layers apply in append order, so `dedupe(..., keep=last)` must match the SAME order records were accumulated in — if the layer whose bytes are semantically "supposed to win" (e.g. the current build, not a stale carried-forward asset) isn't appended last, verify a colliding path is either (a) provably impossible by construction, or (b) explicitly reordered so it wins. |
| 22 | Untrusted-source path-write containment: clean BEFORE prefix-check, not after, plus a second independent containment check at the actual write | For any code that reads a path string from content sourced from something other than the local, already-trusted filesystem (a tar entry from a pulled registry layer, an uploaded archive, any externally-supplied path) and uses it to construct a destination write path under some root directory: is the path cleaned (`path.Clean` for POSIX-style sources like tar entries, `filepath.Clean` for host paths) BEFORE any prefix/allowlist check runs, not after? A raw string can satisfy a `strings.HasPrefix` check while still containing an unresolved `../` that only gets resolved later by `filepath.Join`'s own internal `Clean` — by which point the entry has already been accepted. Separately, and even when the clean-before-check order is right: is there a SECOND, independent check at the actual `os.WriteFile`/`os.Create` call site verifying the final joined path still lies under the destination root (e.g. via `filepath.Rel` or a `destDir+separator` prefix check on the cleaned absolute paths)? Belt-and-suspenders is required here, not optional — the first check is only as strong as every code path that reaches it staying correct, and a future refactor that adds a second call site to the same write logic could easily bypass an early-only check. A regression test for this must prove containment empirically (assert nothing was written outside a real temp directory with a crafted `"../"`-laden entry), not just assert an error was returned — an error from the WRONG cause can still pass a test that only checks `err != nil`. |

See `Lessons.md`'s corresponding entry for the four smaller findings (misdiagnosed start-vs-build failures, a `SysProcAttr`-clobbering assignment, SLSA provenance never actually recording hermetic status, and a bunruntime download path unaware of hermetic mode) from the same review.

Row 19 was added after a 2026-08-18 incident building `--hermetic-mount-isolation` (the `docker.sock` half of `--hermetic`'s residual mount-namespace gap, `internal/adapters/bunexec/hermetic_reexec_linux.go`): the first version of the empirical test overrode the package-level `hermeticMaskPaths` var in the *test process* to point at a disposable test socket, expecting the real masking mechanism to honor it — it didn't, because the actual masking runs inside a **separately-compiled real `pokkum` binary** (built specifically so the test exercises the genuine `__hermetic-reexec` subcommand, since `os.Executable()` inside a `go test` binary resolves to the test binary itself). The bug was caught immediately by actually running the test in a real Linux container (it failed with the socket still reachable) rather than by inspection — but the row exists so the next reexec-adjacent or subcommand-adjacent test catches this class of mistake before running it once, not after. Fixed by adding an explicit, narrow, test-only environment-variable channel instead (same precedent as `bunruntime.Resolver.ReleaseKeyArmored`). See `Lessons.md`'s 2026-08-18 entry.

Row 20 was added after a 2026-08-18 incident building `--asset-overlay`'s Tier 1.1 rolling-deploy feature: `internal/adapters/assetoverlay/assetoverlay.go`'s `extractImmutableAssets` stripped the wrong prefix (`immutableAssetPrefix`, `"app/client/_app/immutable/"`) when writing extracted content into its scratch directory, instead of the client root alone (`clientRootPrefix`, `"app/client/"`) — silently dropping the `_app/immutable/` segment, so repackaging under `AppClientDirPrefix` again produced files at `/app/client/chunks/...` instead of the real `/app/client/_app/immutable/chunks/...` a browser actually requests. The build succeeded, attested correctly, and every unit test passed, because those tests only asserted content landed *somewhere* under the scratch directory with the right bytes, never the exact relative path a real repackage-and-serve round-trip requires. Found only by the plan's own designated row-17-discipline empirical test (`tests/integration/asset_overlay_e2e_test.go`'s `TestRealBuild_AssetOverlay_TwoGenerations`, task #86) — two real, sequential `core.Build`+push runs against a real in-memory registry, inspecting the actually-pushed image's real tar entry names — which is exactly the scenario this checklist's Row 17 exists to force in the first place, just for a static-asset path rather than an executable entrypoint. See `Lessons.md`'s 2026-08-18 asset-overlay entry.

Rows 21–23 were added after a 2026-08-18 adversarial (Opus) review of `--asset-overlay`, run as this codebase's own standing final-review step (CLAUDE.md §6.3) immediately after the feature's full test suite — including a real two-generation empirical test that had *already* caught one severe bug the same day — passed green. The review found four further real, independently-confirmed defects none of that testing caught: (row 21) a second attestation-digest bug, distinct from the earlier same-day one — two OCI layers (the asset overlay and the current build's own client layer) both target `/app/client`, so a path present in both got double-counted in the aggregate digest, since `attestutils.RootDigest` has no dedup of its own; the feature's own test's independent oracle mirrored the same non-dedup bug, so it agreed with the code instead of catching it. (row 22) a real path-traversal vulnerability in `extractImmutableAssets` — a raw, uncleaned tar entry name could satisfy a prefix filter while still containing an unresolved `../` that only got resolved later by `filepath.Join`, escaping the destination directory; the content this filter gates is registry-pulled (auto-discovered chain, or an arbitrary caller-supplied `--asset-overlay-from` ref), not locally-trusted. (row 23) `--asset-overlay-from`'s cross-repository refs always 404'd and hard-failed the build, because `ResolveDigest` returned only a bare digest, silently losing which repository it actually resolved in, while the caller then pulled every resolved digest from its own default repo regardless — directly contradicting the flag's own documented "arbitrary external images" contract. All three were confirmed empirically (a real mismatched digest against a real pushed image; a real file written outside a real temp directory; a real cross-repo build reproducing the exact `NAME_UNKNOWN` failure) before being fixed, and each fix's test was verified to genuinely fail when the fix was temporarily reverted. A fourth, related pair of findings (unbounded `io.ReadAll` on registry content; a malformed predecessor annotation hard-failing the whole chain-walk instead of truncating like the adjacent not-found case) extended existing discipline (row 15's family, and the "fail closed only where earned" principle) rather than needing new rows. See `Lessons.md`'s 2026-08-18 "Adversarial review of `--asset-overlay`" entry for full details, including why the feature's own extensive real-world testing — genuinely rigorous by this project's usual standard — still didn't surface any of these four: ordinary test-writing naturally builds fixtures that exercise the *intended* input shape, not overlapping, malicious, or cross-scope input, which is exactly what a dedicated adversarial pass exists to force.

Rows 16b, 24, 25, and 26 were added 2026-08-18 after a documentation-and-memory-sync pass following a batch of seven fixes on `feat/monorepo-affected2` (image signing wired end-to-end for the first time; keyless verification's self-referential identity bug; secretguard's `bufio.Scanner`/one-match-per-line bugs; two smaller validation-logic bugs in the CVE gate and the Bun SHASUMS parser). The signing incident (row 16b) is a direct, exact recurrence of row 16's own failure mode — `CosignSigner`/`DSSESigner` were required non-nil by validation and never once invoked by the pipeline — which row 16 itself, already in this checklist, would have caught in one grep command had it been run against this exact code; 16b exists to make that specific sub-case unmissable rather than trusting that row 16's broader wording gets applied to every dependency-injection shape. Row 24 generalizes the keyless-identity incident beyond Sigstore specifically: any verification path that derives its expected value from the artifact under test is tautological, and the naive-seeming fix (compare the "real" field instead of the wrong one, but still read it off the same artifact) can be strictly worse than the original bug. Row 25 generalizes the signing incident's actual fix (fetch-back-and-reverify) into a standing design principle for any security control, not just signing. Row 26 generalizes secretguard's bug into a general Go text-scanning trap (`bufio.Scanner`'s 64KB default) that will recur in any future line-oriented scanner over build output. See `Lessons.md`'s five 2026-08-18 entries for full incident detail on each.

Rows 27–31 were added 2026-08-18 after a batch of fixes on `feat/monorepo-affected2` that removed a shared placeholder trust anchor (row 30's origin: `internal/adapters/provenance/resolver.go`'s static-key path was a literal fail-open, `SignatureValid: false` with a `nil` error, found only by applying the same "does this fail closed with no key configured?" proof to a third site after two siblings had already been confirmed fixed) and pinned previously `SOURCE_DATE_EPOCH`-derived immutable-binary layer timestamps (rows 27/28/31's origin: fixing Roadmap item 3f — originally framed as "write a test asserting the Bun layer diffID is stable" — found the diffID was not stable, and writing the fix surfaced two more distinct test-quality bugs in the same area: `tests/integration/e2e_test.go` had an assertion that pinned the *buggy* timestamp behavior as correct, which would have actively resisted the fix, and the new stability regression test needed per-run cache isolation or a shared, now-more-permissive content-only cache key would have made two intentionally-varied builds collapse into one, passing regardless of whether the fix worked). Row 29's origin: the same day's runtime-boot smoke test (`tests/integration/runtime_smoke_test.go`, row 17's test) leaked a Docker container on its own failure path, because `docker run -d --name X` registers the container before starting it, and cleanup had been registered only after a confirmed-successful run. See `Lessons.md`'s five 2026-08-18 entries for full incident detail (git `--since` injection and a `comparator` bounds-check gap were fixed the same day but matched existing rows well enough not to need new ones — the injection fix is row-less process discipline ["reuse a validated value, don't recompute/discard it"] rather than a checklist-shaped code-review check, and the bounds-check gap is already covered by row 2's "every branch" discipline applied to validity checks instead of cleanup).

Rows 32–34 were added 2026-08-19 after a documentation-and-memory-sync pass following a batch of overnight fixes on `feat/monorepo-affected2`: a real `--strategy=static` fixture immediately found three production bugs (a `pokkum-static` bind-address bug rows 32/33/34 don't individually cover but which is its own Lessons.md entry; `Preflight` repeating row 13's exact failure mode; a synthetic fixture repeating row 12's), the composition-root refactor that emptied the adapter-adapter allowlist exposed two more `false, nil`-shaped fail-opens in `provenance` (row 32's origin — the third occurrence of this shape in roughly a day, which is what makes it a named row rather than a one-off note), and the Sigstore trust-root refresh found the embedded snapshot was not merely stale but already rejecting valid signatures, while the embedded PID-1 binaries turned out to be gitignored and built by no CI or release pipeline at all (row 33's origin) and the trust-root fix's own design is row 34's origin — a capture date, a failing-not-warning age test, and a diagnosis that separates "our anchor doesn't cover this" from "this signature is bad." Row 31 was extended, and rows 36–38 added, 2026-08-19 after the final batch of overnight fixes on `feat/monorepo-affected2`. Row 31's extension has two origins: Go's `-buildvcs` default stamped `vcs.revision`/`vcs.time`/`vcs.modified` into the embedded PID-1 binaries, churning their content on every commit even with byte-identical source — the second instance, after `SOURCE_DATE_EPOCH`, of build metadata leaking into these same content-invariant layers; and the blob-freshness guard built to catch exactly this kind of drift initially proved nothing, because its "build twice and compare" reproducibility check ran both builds at one commit and one dirty-state, never varying the dimension (commit-to-commit) that actually matters. Rather than add a sibling row for the second half, row 31 itself was broadened, since both halves are the same underlying class: a build-time value leaking into (or a check failing to vary across) an artifact whose bytes are supposed to be content-determined, not process-determined. Row 36 was added after `cosign verify-attestation` rejected every Pokkum attestation over a missing `dev.cosignproject.cosign/signature` annotation — the assumption that the annotation was signature-only and could be omitted for attestations was encoded in a code comment and never checked against cosign v3's own source, which (via `Base64Signature()`) errors on the annotation *key* being absent regardless of its value, and always writes it as an empty string for attestations. Row 37 was added after the same overnight session found four real issues (three product-side, one in the guide itself) purely by running `paranoid-testing-guide.md`'s commands against a real build rather than reading them — including the guide's own `--output=json`/`jq` extraction, reused in eight places, which could never have worked because `build`'s stdout is deliberately a bare `repo@sha256:...` ref. Row 38 was added after every custom `--base` reference was found to share one `"custom"` `pokkum.lock` slot: resolving custom base B after custom base A had been locked trusted A's entry and silently returned A's image content for a B request — not a cache miss, a wrong answer — reachable only once the CLI gained a way to supply a custom reference at all (the same commit that fixed the CLI gap found this latent lock-collision bug while implementing it). See `Lessons.md`'s 2026-08-19 entries for full incident detail on each.

## Maintenance rule

This table is edited in place, not appended to. Every time a `Lessons.md` entry is logged: check whether its category matches an existing row here.
- If it matches but the row didn't catch it, revise the row's wording so this exact failure mode is unambiguously covered next time.
- If it's a genuinely new category, add a row.

A `Lessons.md` entry with no corresponding update here is a bug likely to recur — this checklist, not the log, is what actually gets run during the next self-review.
