# Self-Review Checklist

A concise, invariant-style checklist run against every non-trivial code diff before declaring it complete, as part of the verification protocol in `mem:task_completion`. Unlike `Lessons.md` (an append-only, chronological incident log kept in the repo root), this memory holds only the *currently-active, distilled* rules and is edited in place, not appended to — that's why it lives in Serena rather than the log itself.

Shared across every agent/harness working this codebase (each has Serena access) — this is the one source of truth for the checklist; do not fork a duplicate copy into a harness-specific instruction file.

## How to use

1. After a diff is otherwise ready (tests green, `make verify` passing per `mem:task_completion`), walk every row below against the actual diff lines — not from memory of having read it once.
2. If a row doesn't apply, say so explicitly ("N/A: no concurrent dispatch in this diff") rather than skipping it silently.
3. If a bug is found during this pass, log the root cause and preventative rule in `Lessons.md` (repo root), then come back and close the loop here (see Maintenance rule below).

## Checklist

| # | Check | How to verify |
|---|-------|----------------|
| 1 | Fan-out error paths | For every `errgroup.Group`, `sync.WaitGroup`, or bare `go func()` touched by the diff: grep for every `return`/`continue`/`break` sitting between the dispatch call and its corresponding `Wait()`/`Done()`. Each one is a leak candidate until you can point to why it's safe. |
| 2 | Resource cleanup on every branch | For every `os.File`, `io.Reader`/`io.Closer`, network conn, or lock acquired in the diff: trace every return path, including new early-return branches just added, and confirm cleanup runs on each — not just the happy path. |
| 3 | Multi-item collection logic | If the diff processes a collection (map, slice, multi-document stream), does at least one test use ≥2 items with *differing* content/outcome? Single-item or all-identical fixtures hide item-interaction bugs. |
| 4 | Non-first-item failure injection | For every new error path inside a loop or fan-out, does a test trigger the error on a *non-first* item, not just the first/only one? A single-item error test can pass while a real multi-item failure leaks resources. |
| 5 | Ordering / determinism | Are map iterations, directory traversals, and concurrently-produced results consumed in an explicitly sorted or otherwise deterministic order (bit-for-bit reproducibility invariant, `mem:core`)? |
| 6 | Clock / timestamp access | Does the diff introduce any `time.Now()` or system clock read outside `req.SourceDateEpoch`? |
| 7 | Go version regression | Does the diff touch `go.mod`'s `go` directive or any `go-version:` line in `.github/workflows/*.yml`? If so, `git diff` those exact lines and confirm the version only holds steady or increases — never decreases. |
| 9 | Runtime-vs-construction validation | Does the diff rely on a precondition that can change at runtime (a file's existence/type, openness) but only validate it once at construction/setup? If so, the code path must re-check the precondition at the point of use and degrade to the normal-miss path, never escalate to 5xx or serve stale state. |
| 8 | golangci-lint clean | Has `golangci-lint run ./...` (or `make lint`, folded into `make verify` as of the step below) actually been run against this diff — not just `go vet`? `gofmt`/`go vet`/`go test` all pass on findings golangci-lint alone catches (`errcheck`, `staticcheck`, ...); see the Origin note below. |
| 10 | Base-vs-profile config field parity — validation AND merge | If the diff adds, removes, or changes a `ports.ImageConfig`/`ports.ProjectConfig` field: (a) does `cmd/pokkum/config.go`'s `runConfigValidate` (or the shared `validateConfigFields` helper) apply the same check to it via the per-profile iteration over `cfg.Profiles`, not just the base-config call? (b) separately — a distinct function, a distinct miss — does `internal/adapters/config/config.go`'s `ApplyProfile` include an explicit `if profile.Image.X != zero { merged.Image.X = profile.Image.X }` line for it? `ApplyProfile` is hand-written per-field, not reflection-based, so a new struct field is silently invisible to `--profile <name>` (parses fine, validates fine, then discarded) unless a matching merge line is added — this is a *second*, independent place the same new field can be forgotten, not covered by fixing (a) alone. Grep both `runConfigValidate` and `ApplyProfile` for the new field name; both must appear, or say explicitly which one legitimately doesn't apply and why. |
| 11 | Strategy-gated logic scoped to the right strategy | For any `if`/`switch`/`else` in `internal/adapters/bunexec`, `internal/adapters/packager`, or `internal/core/pipeline.go` that branches on `req.Strategy`/`ports.BuildStrategy`: is an `else`/`default` arm actually correct for *every* strategy it covers, or was it written assuming only one specific strategy would ever reach it? A negative check (`!= StrategyX`, "not static") is not the same as a positive check (`== StrategyY`) — the former silently includes every future or existing strategy nobody thought about when the branch was written. Trace which strategies actually execute the branch and confirm each one's real toolchain output matches what the branch assumes. |
| 12 | Fixture fidelity to the real consumed artifact — and its provenance claim | For a fixture/mock claiming to be "real" (sourced from an actual upstream package, a real tool run, a real npm package, etc.): is it sourced from the *exact pipeline stage* the code under test actually reads — or from an earlier stage (e.g. a package's source template) that merely resembles the final artifact? A fake-bun/fake-tool test harness's fixture content must model what the real tool would emit for that exact code path, not just whatever satisfies the current implementation — check this by asking "would running the real tool right now actually produce this?", not "does this fixture make the test pass?". A doc comment asserting "captured verbatim from a real run of X" is itself a claim to verify, not evidence on its own — especially for a sub-agent-authored fixture — so if the real command is runnable in this environment, actually re-run it and diff the output before trusting the comment. |
| 13 | Caller-chain coverage for a same-diff fix | If the diff fixes function B, and B is called by A before some other check in A runs (or by C after B), does at least one test exercise A (or C) end-to-end with the same real-world input the fix targets — not just B in isolation? A thoroughly unit-tested fix can still leave the real call chain broken if a sibling check earlier or later in the same chain was never revisited. Grep the fixed function's callers; if any of them do their own independent validation before/after calling it, that caller needs its own test with the fix's target input, not just the fixed function. |
| 14 | Auto-fix/auto-inject features need a fixture the feature is meant to fix | For a diff touching a feature whose entire point is to correct, inject, or paper over a misconfiguration (zero-config injection, auto-repair, `--fix` flags, defaulting logic): does at least one test fixture start in the *broken* state the feature exists to handle, not only already-correct fixtures? A fixture that's already correct can pass every assertion whether or not the feature under test does anything at all — it structurally cannot tell you the feature works. |
| 15 | External compiler/tool output determinism, and unverified non-determinism hypotheses | For any diff invoking an external compiler/tool (`exec.Command`) whose output becomes a shipped artifact (embedded binary, layer content): if any argument or `cmd.Dir` is an absolute path that varies per invocation (an `os.MkdirTemp` directory, PID, timestamp), does the artifact's byte-identity depend on that path? Verify empirically — run the exact production invocation shape twice with only that one input varied and diff the output — rather than shipping a fix based on a plausible-sounding but unverified mechanism (linker build-id, ASLR, embedded timestamps). A repro that changes two things at once (e.g. both the output filename and the source path) can implicate the wrong mechanism entirely; isolate one variable at a time before designing the fix. |
| 16 | Feature reality check before marking `[x]`/Done, and before *starting* a fix for a roadmap item's problem statement; test-shape vs. test-substance | Before checking off a `Roadmap.md` item or marking an `AdditionalFeatures.md` matrix row Done — and before trusting an existing check that already looks satisfied — grep the implementing file for the I/O primitive the feature's description necessarily requires: a command claiming to inspect a remote image must reference `remote.`/`Fetch`/a tar reader somewhere; a claimed endpoint must register a handler for that exact path; a claimed emitted field must contain that field's literal name in the producing code. Absence of the required primitive is proof of absence of the feature, full stop — a passing test is not counter-evidence if the test only asserts output *shape* (correct JSON keys, correct exit code) rather than asserting the output was *derived from real input* (e.g. a digest that changes when the underlying image changes). For a feature named with "X and Y" (two halves in one description, one flag, or one row): verify each half independently: it is common for one half to be real and the other a stub, and a test exercising only the real half will pass cleanly while the row still overclaims. **The mirror case, at the start rather than the end of a fix:** an *open* roadmap item's problem statement is also an unverified claim — if it says "`--some-flag` triggers X," grep `cmd/pokkum/*.go`'s actual flag registrations for that exact flag name before starting. A Go struct field or port request parameter existing is not evidence a CLI flag reaches it; the field can be real and correctly consumed while the flag that's supposed to set it was never wired at all, making the "fix" invisible from the CLI until that's caught too (see `Lessons.md`'s 2026-08-17 `--bun-version` entry). **Same discipline applies to a documented invocation path, not just a documented feature or flag**: when rewriting or verifying a command's docs, run `--help` (or `go run ./cmd/pokkum <claimed-path> --help`) against the actual built binary and diff it against what the docs claim the command line looks like — a subcommand nested under a different parent than the docs describe (`pokkum explain why` documented as top-level `pokkum why`) is the same class of unverified claim as a fabricated field, just cheaper to check (see `Lessons.md`'s 2026-08-17 `pokkum why`/`pokkum diff` entry). **Also check field-level provenance within an otherwise-real feature**: for each field in a new "reads real data" command's output, does it come from the *resolved/verified* result, or does it just echo an *input parameter* (a flag, a request field) that only some of the function's code paths actually use to produce that result? An echoed-but-unverified input looks identical to a real observation in every unit test that happens to pass a value already consistent with the fixture — it only diverges against a real input crafted to disagree, which is exactly why a manual smoke test against a real build (not just synthetic fixtures) caught this once already (see `Lessons.md`'s 2026-08-17 `pokkum explain`'s `Platform` field entry). |
| 17 | Packaged output must actually execute, not just exist with the right bytes | For any change to what gets packaged into a container layer (`internal/adapters/packager/*`, `internal/core/pipeline.go`'s `pkgReq.*Dir` assignments, anything touching `AppServerDir`/`AppClientDir`/etc.): extract the actual built layer from a real end-to-end build (a real fixture, not a synthetic mock) and run its entrypoint (or the specific artifact) directly — `tar -xzf` the layer blob, `cd` into it, execute it, confirm it actually starts/serves. Tar-member presence, byte-for-byte determinism, and digest stability tests (which this codebase has many of) prove none of this — a file can be present, byte-correct, and still fail to run once extracted into its real sibling directory structure (e.g. a relative import that assumed a different nesting). If the only test coverage for a packaging change is a synthetic mock's directory shape, confirm that mock's shape was itself checked against a real build of the real upstream tool (adapter-node, Bun, etc.) — a mock can encode the same wrong assumption as the bug it's meant to catch. |

## Origin

Rows 1 and 4 were added after a real goroutine-leak bug in `internal/adapters/k8s/resolver.go`'s monorepo affected-detection fan-out loop (`mem:core`'s Monorepo Affected-Detection entry): an `AffectedDetector` error on a non-first project path returned before `g.Wait()`, orphaning already-dispatched build goroutines. The only existing test for that error path used a single-project manifest, so it passed without ever exercising the leak — the bug survived a prior instruction that told agents, in prose, to "scan for goroutine leaks," because nothing forced a concrete check against the specific lines where it mattered. Row 3 generalizes the same lesson from an independently-found multi-document YAML annotation cross-contamination bug in the same code area.

Row 9 was added after a `supervisor/cmd/pokkum-static` SPA-fallback bug where the fallback file was validated as a regular file at construction but the serve path never re-checked it at request time, so a deletion surfaced a 500 instead of the documented 404-miss. Same Preventive rule family as Row 2 but distinct: Row 2 is about *resource cleanup on every branch*; Row 9 is about *validating a mutable runtime precondition at the point of use, not just at construction*.

Row 8 was added after a `Lessons.md` entry ("The 4-step verification suite does not run golangci-lint") documented a CI-breaking `errcheck` finding that survived every "green" report from the then-current verification protocol — `make verify` ran fmt/vet/tests/build but never lint, so a change could pass every step described in `mem:task_completion` and still fail CI on the first push. `make verify` now runs `golangci-lint run ./...` as Step 2/5 (see the Makefile), closing the gap the row exists to catch if that step is ever skipped or bypassed. Row 7 was added directly (not from a `Lessons.md` incident) per an explicit user instruction: never downgrade the Go toolchain version.

Row 10 was added after a `Lessons.md` entry (".pokkum.yaml config validation had three silent-failure gaps") found that `pokkum config validate` checked only the top-level `ProjectConfig` fields — a profile with an invalid `strategy`/`base`/`sbom`/`docker.repo` passed silently because nothing forced the same checks to run per-profile when profile support was added on top of an already-shipped top-level validator. `runConfigValidate` now extracts a shared `validateConfigFields` helper called once for the base config and once per profile; row 10 exists so the next field added to either struct doesn't quietly reintroduce the same asymmetry.

Row 11 was added after a `Lessons.md` entry ("`assets.generated.ts` normalization ran for `StrategyLayered`") found that `compiler.go`'s non-static `else` branch ran a `@jesterkit/exe-sveltekit`-only normalization step for `StrategyLayered` too, because the branch was written as "not static" instead of "is exe" back when only two strategies existed and never revisited when `StrategyLayered` was added — a real `--strategy=layered` build (the default) failed on every run against its own documented adapter. The bug shipped and stayed hidden because the same day's own golden-master test's "layered" fixture fabricated the file the buggy code expected, satisfying the bug instead of catching it (see row 12). Row 11 exists so the next new strategy, or the next branch added to this same dispatch code, gets checked against "is this arm correct for every strategy that reaches it," not just "does it compile and pass the existing tests."

Row 12 was added after the same incident's follow-up: `prerendered_patch.go`'s regression tests (added the same day, sourced from real `npm pack`'d adapter-node packages) still failed to catch that `patchPrerenderedHandler` cannot patch a *real, freshly-built* project's `handler.js` — because the checked-in fixture was adapter-node's pre-bundling source template, and the actual file the patcher reads is Vite/Rollup's bundled output, which restructures the code enough that none of the known patterns survive. "Sourced from a real npm package" felt like sufficient rigor and wasn't — it was still one pipeline stage removed from what the code under test actually consumes. That gap was fixed 2026-08-17 (see `Lessons.md`) not by adding new patterns but by discovering the matching logic itself was fine — the real bundled `handler.js` is a re-export barrel pointing at a content-hashed chunk file that still contains an exact, unchanged match of one of the existing 8 patterns; the fix was following the re-export, not rewriting the matcher. Row 12's wording was extended 2026-08-17 after a distinct but closely related incident the same day: a sub-agent-authored fixture (`compiler_strategy_test.go`'s `svCreateSvelteConfigFmt`) carried a doc comment claiming it was "captured verbatim from a real `bunx sv create` project" — untrue, caught only because adversarial review actually re-ran the claimed command. The fixture content itself was fine; the unverified provenance *claim* was the bug. See `Lessons.md`'s corresponding entry.

Row 13 was added after a same-day (2026-08-17) incident in the same area: a well-tested fix to `bunexec.Compiler.Prepare`'s adapter detection (`checkEffectiveAdapter`) still left every real `sv create` project unbuildable, because `Preflight` — a separate, earlier check in the real `core.Build` call chain that the unit/`Prepare`-level tests never exercised — independently and unconditionally required `svelte.config.js` to exist. Only an end-to-end test that called `core.Build` (not `Prepare` directly) against a real, `svelte.config.js`-less project surfaced it. Row 13 exists so a fix that's thoroughly tested at the function level doesn't get declared complete without checking whether anything else in the same real call chain makes an independent, untested assumption about the same input.

Row 14 was added after the root incident behind rows 12/13/this file's whole 2026-08-17 cluster: v0.2's "Zero-Config Auto-Injection" feature shipped with a virtual-config-writing code path that nothing ever read, undetected for two versions, because the one real-`bun` regression fixture (`sveltekit-basic`) has its adapter already hand-configured correctly — every test asserted things that would be equally true whether or not the injection feature did anything at all. Row 14 exists so the next "auto-*" feature's tests include a fixture that starts broken, not only fixtures that were already fine.

Row 15 was added after a 2026-08-16 incident (`Lessons.md`'s stub-launcher determinism entry): `bunruntime.compileStub` compiled a constant-content entry file from inside a fresh `os.MkdirTemp` directory on every call and passed its absolute path to `bun build --compile`, making the compiled `--stub-launcher` binary non-deterministic — a direct violation of the bit-for-bit OCI reproducibility invariant, undetected because no existing test invoked the real `bun` compiler. A prior handoff document had already isolated *that* the binary was non-deterministic but not *why*, and shipped a plausible-but-wrong hypothesis (ELF `.note.gnu.build-id` linker randomness) as the leading fix candidate, based on a repro that varied two things at once (`--outfile` name *and* implicitly the build). Isolating one variable at a time (fixed outfile, varying entry path vs. fixed entry path, varying outfile) found the real cause in minutes and led to a far simpler fix (relative entry path + `cmd.Dir`) than the originally-proposed ELF binary patching. Row 15 exists so a "confirmed bug, plausible root cause" handoff still gets its root-cause hypothesis verified before a fix is designed around it — a wrong-but-plausible diagnosis can send an otherwise-careful fix down a much more complex path than the bug actually needs.

Row 16 was added after a 2026-08-17 documentation-audit incident: `pokkum explain`/`why`/`diff` shipped as three fully-wired cobra commands, marked `[x]` in `Roadmap.md`'s v0.4 milestone and `Done` in `AdditionalFeatures.md`'s matrix, while `cmd/pokkum/explain.go` returned hardcoded literals (`Digest: "sha256:base..."`, a hardcoded `layer_index: 3`, a hardcoded `modified` list) for every input — no `remote.`, `Fetch`, or tar reader anywhere in the file. `explain_test.go` passed throughout, because it asserted the response's JSON shape, which the hardcoded data satisfies regardless of whether any real image was ever read. Three further matrix rows (supervisor `/metrics`, app-side trace-context logging, Helm/Kustomize GitOps export) were separately found marked Done while only one of their two described halves was built. The gap was found not by code review of Pokkum's own diffs but by verifying an external reviewer's claims against the code instead of against the project's own docs — the second time this project's own audit process (see `fixes-to-v1.md`) has caught this exact drift class, making it a recurring failure mode rather than a one-off. See `Lessons.md`'s 2026-08-17 entry and `Roadmap.md`'s Pre-Publication Gate (item PB-1).

Row 17 was added after the most severe bug found in this project so far: every `--strategy=layered` (default) image built by this codebase since its very first commit was missing its own entrypoint (`/app/server/index.js`) — `internal/core/pipeline.go` packaged only the SvelteKit build output's `server/` subdirectory, but a real `@sveltejs/adapter-node` build emits `index.js` as a sibling of `server/`, not inside it. Every layer/packaging test in the repo (golden digests, determinism, layer-content assertions) checks structure and bytes, never whether the packaged result actually runs — and the one test that modeled the layered strategy's directory shape at all (`tests/integration/e2e_test.go`'s `mockCompiler.Prepare`) encoded the exact same wrong assumption the production code had, so it could never have caught this. Found only by manually building a real fixture, extracting the actual packaged layer from the resulting OCI tarball, and running `bun index.js` against it directly — which crashed, twice, surfacing first the missing entrypoint and then (after an incomplete first fix) a second, deeper issue where flattening `server/` into `/app/server` broke `../../`-style relative imports chunk files use to reach siblings like `shims.js`. See `Lessons.md`'s corresponding entry for the full fix (`pruneutils.ExcludeDirs`, packaging the whole build output instead of flattening a subdirectory).

## Maintenance rule

This table is edited in place, not appended to. Every time a `Lessons.md` entry is logged: check whether its category matches an existing row here.
- If it matches but the row didn't catch it, revise the row's wording so this exact failure mode is unambiguously covered next time.
- If it's a genuinely new category, add a row.

A `Lessons.md` entry with no corresponding update here is a bug likely to recur — this checklist, not the log, is what actually gets run during the next self-review.
